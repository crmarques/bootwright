# Ceph apply and destroy audit

**Assessed 2026-11-20.** Bootwright `1e9f77aedd3bd0ff1df1a9f2e38b7d52bc36e566`. Companion input charts `9f7fd46e0b95d0957f6e724a016f2577b414101b`. Codex performed the review.

## Assessment

**A successful plan does not establish a working destroy for the published physical stretch example.** Its data hosts retain their roots, its core deploys a crash daemon on each host, and its tiebreaker is provided. Those choices expose three independent destroy failures. The first involves reaching the stopped host, the second proving the ownership of the daemons present there, and the third releasing the provided host's preparation block. Correcting any one still leaves the others.

Ordinary clusters also have material findings. In particular, two legal pool names can collide in Bootwright's journal, and a native pool created concurrently by another administrator can be mistaken for this apply's creation. Virtual whole-cluster retirement avoids the retained-root path. Its success says little about the physical inverse.

The audit identified 13 findings across the two flows, eight high and five medium. High findings can prevent a supported lifecycle from completing, defeat site resilience, or apply settings to someone else's resource. Medium findings admit inputs that fail late, misdirect operators, or leave a bounded gap in recovery or verification. Each finding below identifies which conclusion was exercised offline and which follows from source inspection.

## Destroy findings

### D1 · High · Retained-root cleanup needs SSH after destroy has required power off

A fresh destroy requires every managed target to be off or absent before registration. The retained-root Ceph host inverse then calls the guest cleanup worker over SSH. It never starts the identified Machine. Subscription unregistration can start a guest for its own cleanup, but stops it after recording release. Consequently a properly stopped physical host cannot answer the Ceph call on the ordinary path. A registered continuation can have different power conditions, which explains why manually changing power can move the failure without repairing the workflow. This is a source-traced failure of autonomous cleanup. [Entry gate](../../internal/reconciliation/lifecycle/start_power.go#L117) · [Ceph host inverse](../../internal/storage/ceph/host.go#L774) · [SSH cleanup call](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_core.py#L1277) · [Existing registered start, receipt and stop](../../internal/managedos/installation/removal_power.go#L51)

### D2 · High · The retained-root worker rejects a daemon Bootwright deploys on every host

The core adds the delegated `crash` service to every host. The host-preparation request drops delegated service identities. Physical cleanup sends this narrower request to the production daemon observer, which requires each delegated daemon to match a service listed for that host. Given `crash.member` and its correct service metadata, the observer's selection functions refuse with `native-observation-unproved` under the host request and accept it under the cluster request. This blocks cleanup while the crash daemon layout remains, even if SSH works. Optional RGW and monitoring daemons widen exposure. The retained-root unit fixture substitutes its daemon inventory, masking the production boundary. The provided arbiter's *cluster-level* cleanup receives the wider request. [Crash placement](../../internal/storage/ceph/requests.go#L459) · [Host scope](../../internal/storage/ceph/requests.go#L340) · [Physical worker](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_stretch.py#L863) · [Service matching](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_observe.py#L313) · [Fixture](../../ansible/collections/ansible_collections/bootwright/core/tests/unit/plugins/module_utils/test_ceph_tiebreaker_removal.py#L71)

### D3 · High · A provided arbiter is sent to the physical-host inverse

The planner emits a preparation block for every member. Both host `Destroy` and `ObserveRemoval` select the physical branch when **any** member is physical. The callee requires the **target** to be physical. A provided arbiter therefore receives an inconsistent-policy error, including after its dedicated cluster inverse removed its footprint. Replacing credentials or retrying the frozen request cannot change the target type. The virtual-data-host stretch rehearsal does not exercise this combination. [Host planning](../../internal/storage/ceph/host.go#L318) · [Destroy dispatch](../../internal/storage/ceph/host.go#L638) · [Observation dispatch](../../internal/storage/ceph/host.go#L678) · [Target guard](../../internal/storage/ceph/physical_retirement_proof.go#L383) · [Provided host](../../internal/storage/ceph/provided_host.go#L59)

### D4 · High · Destroy demands a cleanup receipt from host preparation that never ran

Consider an apply that installed a physical OS, retained the root, then stopped before Ceph host preparation or bootstrap, for example during image resolution. Removal includes started blocks only. The OS installation has started, so the uninstalled-machine exception is inapplicable. Terminal retirement demands the host-cleanup receipt, but the pending host block has no inverse in this removal. Continuing cannot produce that receipt. This failure can surface at terminal verification, after earlier inverses have already run. The distinction that matters is whether this host ever began Ceph preparation, independently of whether its OS was installed. [Removal subset](../../internal/reconciliation/stage.go#L227) · [Installation-state check](../../internal/managedos/physicalerase/unstarted.go#L43) · [Terminal decision](../../internal/storage/ceph/physical_retirement_proof.go#L109) · [Missing receipt](../../internal/storage/ceph/physical_retirement_proof.go#L394)

### D5 · High · An installed physical MON-only host with no erase target cannot retire as specified

The physical policy admits a retained root with zero selected Ceph disks and zero erase targets. The terminal verifier even accepts a cleanup-only receipt for that case. Earlier, the lifecycle engine requires every installed member to have a host-removal block. The physical erase capability creates one only for Machines with erase targets. With an installed, diskless MON host, the cluster consequently reports a surviving host before native cleanup can run. This concerns the installed variant of the arbiter or another installed MON-only member. The example's provided arbiter takes D3 instead. [Policy](../../internal/storage/ceph/physical_retirement.go#L172) · [Cleanup-only receipt](../../internal/storage/ceph/physical_retirement_proof.go#L129) · [Host-removal gate](../../internal/reconciliation/lifecycle/removal_phases.go#L128) · [Erase planning](../../internal/managedos/physicalerase/capability.go#L56) · [Cluster refusal](../../internal/storage/ceph/capability.go#L572)

### D6 · Medium · The native cleanup receipt covers fewer files than the removal command can affect

On a surviving OS, the worker probes FSID data, logs, logrotate, unit files, the FSID in `ceph.conf`, the recorded SSH key, registry credential and route. The native command can also touch shared files and the admin keyring. The probe does not independently read the keyring or `ceph.pub`. If the config and scoped directories disappear first, the remaining footprint check can succeed with a residual file. Conversely, a clean FSID inventory does not establish ownership of every shared file the provider might remove. The spec identifies the provider footprint as unverified. This is a gap in the evidence behind the receipt. Actual residue or deletion on a selected IBM build remains unmeasured. [Observed files](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_stretch.py#L736) · [Completion check](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_stretch.py#L820) · [Effect and absence contract](../../specs/ceph.md#a-provided-tiebreakers-removal) · [Provider cleanup analysis](../../.agents/knowledge/ibm-ceph-cleanup.md)

### D7 · Medium · Ordinary and stretched runbooks promise cleanup on an invocation that refuses at entry

Both runbooks run a fresh destroy with managed Machines still running and describe successful online cleanup followed by a pause. Current admission refuses with `lifecycle.start-power` before registration, unregistration or arbiter cleanup. The later stop and destroy commands can still initiate removal. Operators following the text will misinterpret the first refusal and their evidence will omit the claimed phase. In the two-context rehearsal, the provided arbiter must remain reachable while the managed data Machines are stopped. ## Apply findings

### A1 · High · A concurrent native pool creation can be attributed to Bootwright

The worker lists pools, records intent, calls native create, then binds the ID of the first same-name pool it reads back. The uninterrupted path checks the name and cardinality before binding. The lost-reply path additionally checks the creation shape. Upstream Ceph v20.2.1 returns success when a pool of the requested name and type already exists. If another writer creates it after the initial list, Bootwright can record the other pool's ID and proceed to change its replica settings. A later readiness failure cannot undo those settings. This is an inference from the two implementations. The selected IBM build and a live race were not exercised. Matching shape alone would still leave an identically shaped foreign pool ambiguous. [Bootwright creation and ID binding](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_resources.py#L333) · [Replica changes](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_resources.py#L391) · [Upstream monitor response](https://github.com/ceph/ceph/blob/v20.2.1/src/mon/OSDMonitor.cc#L12944-L12955)

### A2 · High · Two legal pool names share a recovery record

For a pool `data`, the native ID is recorded as `pool-id-data.json`. For a pool `id-data`, the desired owner record is also `pool-id-data.json`. Both live in the same FSID directory and require different content. An offline run of the real resource worker against a scripted monitor and shared marker store produced `ownership` when `data` ran first, and `pool-identity` when `id-data` ran first. Serializing the blocks does not help. A cluster with one pool can run normally, then fail when an otherwise valid second pool is included in a fresh desired state. [Marker construction and reads](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_resources.py#L337) · [ID publication](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_resources.py#L365)

### A3 · High · Eligible MON hosts can pass stretch admission with an impossible or fragile quorum

A five-host MON selector with `placement.count` of one or two passed validation and planning. The worker then requires exactly that count, the tiebreaker and a MON at each of two data sites. No one- or two-MON placement can satisfy all three requirements. There is a second failure mode. An explicitly unbalanced placement with two MONs on one data site, one on the other and one arbiter validates. Losing the two-MON site leaves two of four, short of a majority. The Helm example protects its balanced placement, while direct Bootwright inputs can reach these states. The impossible counts were checked with the real planner. The site-loss outcome follows from quorum arithmetic. [Admission](../../internal/storage/cephcluster/topology.go#L292) · [Count projection](../../internal/storage/ceph/services.go#L54) · [Native placement predicate](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_stretch.py#L231)

### A4 · Medium · Go accepts host identities the native worker cannot identify

Two distinct registered FQDNs with the same first DNS label pass admission. A DNS-valid 139-character FQDN also passes. Both ordinary chart variants built complete graphs. Native validation requires unique short labels and bounds a host name to 128 characters. MON/MGR identity resolution also derives daemon identities from the first label. The error reaches an adapter after planning and can follow machine provisioning. The optional consumer's MON-name check only helps plans containing that consumer. [Go topology admission](../../internal/storage/cephcluster/topology.go#L178) · [Native host admission](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_validate.py#L132) · [Daemon mapping](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native.py#L880) · [Consumer check](../../internal/storage/ceph/export.go#L341)

### A5 · Medium · A reserved stretch rule survives validation and planning

Setting `spec.topology.stretch.ruleName` to `replicated_rule` in the published stretch render produced a valid apply and inverse graph. The worker explicitly refuses the bootstrap-owned rule. Go's admission already checks the reserved name and grammar for a CephPlacementPolicy, but the stretch field only needs to be nonempty. This particular variant should fail at the authored field before a Machine is provisioned. [Public field](../../api/v1alpha1/storage.go#L69) · [Placement-policy check](../../internal/storage/cephcluster/pools.go#L160) · [Stretch request](../../internal/storage/ceph/stretch.go#L35) · [Native refusal](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_stretch.py#L76)

### A6 · Medium · A host crash during registry credential preparation can block the next apply

The worker creates a private anchor, writes the credential, syncs the file and directory, then publishes the pending record identifying the inode. A machine failure between those durable writes can leave a private anchor with no binding. On retry, the ownership guard correctly refuses an unbound anchor. The exception handler removes its own file during normal unwinding, which a hard stop cannot guarantee. The consequence is a manual recovery boundary during ordinary bootstrap. The evidence establishes the ordering and the refusal, without an observed host crash or credential disclosure. [Publication order](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_registry.py#L210) · [Retry guard](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_registry.py#L173)

## Known limits that change the recovery decision

| Situation | Behavior and practical consequence |
| --- | --- |
| Bootstrap has deployed a daemon on another host and the cluster is still incomplete | A later apply may refuse `partial-cluster`. If native convergence cannot complete independently, recovery can require whole-cluster retirement. B659 owns forward recovery. [Bootstrap continuation](../../specs/ceph.md#bootstrap-identity-and-continuation) |
| Stretch activation stopped inside a multi-command stage | Once the attempt exists, retry completes only if the full postcondition already holds. A partially applied stage can return `stretch-interrupted` indefinitely. B920 tracks forward recovery. On a physical chart the fallback retirement itself encounters D1–D3. [Activation journal](../../ansible/collections/ansible_collections/bootwright/core/plugins/module_utils/ceph_native_stretch.py#L164) · [B920](../../specs/milestones/m2.md#b920) |
| A host, storage consumer or its workload survives | Generic online removal and per-resource revocation remain out of scope under B491. A CephConsumer on physical hosts explicitly refuses even when the physical disks have complete erase policies. The emitted generic surviving-host remedy can suggest virtual retirement to an operator who already has physical hosts. A fresh-plan warning should name the exact blocking object and policy. [Consumer gate](../../internal/storage/ceph/export_evidence.go#L237) · [Removal contract](../../specs/ceph.md#removal-and-concurrency) |
| A physical OSD, DB or WAL device lacks original erase authority | A plan can freeze this choice and apply can proceed. Destroy cannot add erase authority retrospectively. Report retirement eligibility before apply, including the uncovered device and Machine. [Original-policy check](../../internal/storage/ceph/physical_retirement.go#L172) · [Apply policy receipt](../../internal/storage/ceph/physical_retirement_proof.go#L66) |
| The provided arbiter was reinstalled or permanently removed first | Its original identity and absence cannot be proved by contacting the original host. Preserve it through the Ceph context's destroy. B938 tracks the exit for permanent loss. [Stretch runbook](../../e2e/lab-5-nodes-ceph-stretch/runbook.md#destroy) · [B938](../../specs/milestones/m2.md#b938) |

## Recommendations in priority order

1. **Restore a complete physical destroy before qualifying either physical chart.** Dispatch host release using the target's substrate (D3). Give retained-root cleanup a registered start, durable FSID-scoped receipt and verified shutdown (D1). Supply an exact per-host list of owned daemons to the cleanup observer (D2). Exercise these together on a multi-host plan with a provided arbiter, a mandatory crash daemon and an optional gateway. Interrupt after native release and before shutdown. A successful continuation must preserve foreign state, avoid repeating completed work and produce receipts for every authorized disk.
2. **Close both partial-retirement gaps.** Use the sealed original per-host preparation state to handle an installed Machine on which Ceph never started (D4). Represent cleanup-only retirement for an installed MON-only host with no erase targets (D5). Include missing or contradictory evidence as negative cases. Preserve the existing refusal when a selected data disk lacks authority. Verify the full path from a fresh destroy through terminal evidence and claim release.
3. **Require proof of pool creation before changing protection.** Capture and qualify the provider's distinct created/already-existed outcome. Refuse ambiguous creation before adopting a native ID or setting size, min_size or options (A1). Use unambiguous typed journal keys for pools and review other resource markers built from names (A2). Test both pool orders, a lost create reply, and a pre-existing same-type pool with different protection. The foreign pool must retain its settings.
4. **Make admission predict the native placement and identity checks.** Reject unrealizable counts and placements that cannot retain a majority after loss of either data site. Apply the same short-name, length and reserved-rule checks to direct desired state and chart output (A3–A5). Run each negative fixture through validation and assert that its diagnostic points to the authored field.
5. **Qualify the remaining crash and absence boundaries.** Make the credential anchor recoverable across every durable publication boundary while preserving the refusal to adopt a foreign inode (A6). Extend cleanup evidence to the owned files and live runtime objects that the qualified provider can leave or remove (D6). Exercise interrupted stretch activation and first enrollment under B920 and B659 before relying on retirement as the fallback.
6. **Correct operator guidance and run acceptance against the shipped shapes.** Put the managed-host stop before the first fresh destroy, keep the provided arbiter reachable, and show the actual entry refusal separately from a registered pause (D7). Publish pre-apply retirement warnings for original erase coverage and physical consumers. After the offline regressions pass, run the ordinary virtual, ordinary physical and provided-arbiter stretch journeys on owner-approved targets, recording client I/O, site loss and recovery, destroy, and post-destroy evidence.

# M2 — Full IBM Ceph provisioning

Define managed IBM Ceph 9.9.x delivery in [M2a](#m2a), then provision, verify,
continue and destroy it through [M2b](#m2b)'s minimal virtual cluster,
[M2c](#m2c)'s full virtual coverage, [M2d](#m2d)'s full physical coverage and
[M2e](#m2e)'s provider-supported stretch configurations (D129 to D131).
Full coverage means every
supported provisioning row of the [provider matrix](../storage-coverage.md),
using separate profiles where topology, capacity or native restrictions differ.
M2 supports all IBM-supported cluster sizes for the qualified release and
deployment mode on both provider paths (D130); the checkpoint profiles are
acceptance examples.
The [provider size and feature rules](../storage-coverage.md#release-qualification)
govern admission and qualification, including larger service-specific profiles.
The [storage contract](../storage.md) owns runtime requirements; the
[product scope](../project.md#product-scope) retains the bootstrap boundary.

## Submilestones

M2a to M2e are stable submilestone IDs within M2, introduced on 2026-10-11
(D131). They group definition and delivery outcomes; M2 retains its single
milestone status and its B/X identifiers. A submilestone is not an active
slice and grants no implementation authority. The retired M2a/M2b aliases
from before 2026-09-28 keep their historical meanings; current references
link to the definitions below.

| ID | Outcome | Work mapping |
| --- | --- | --- |

| [M2b](#m2b) | Simple three-node Ceph cluster on libvirt+sushy | X52, X47, X53, X70, X54; operator exit B476 |
| [M2c](#m2c) | Full-featured Ceph on libvirt+sushy | X55 to X61; operator exit B484 |

### M2a

Review and define the full scope and every implementation task: provider
coverage, domain contracts, typed-input gaps, owners, dependencies, bounded
outcomes, release/size constraints, promotion decisions and executable exit
evidence. B472 owns the release definition; every other item owns its detailed
contract questions. **Exit:** a reviewed, traceable definition baseline for
M2b to M2e, with each unresolved promotion gate explicitly assigned. A task
whose contract or exact release remains unresolved is not ready to implement.
Accepting the planning baseline completes no executable backlog item or
operator gate. B315 to B317's fixes, B474's projection and B490's probes remain
X52 implementation in M2b. Definition is allowed while M1 remains open.

The [Ceph API review](../storage-api-review.md) is part of M2a (D132): review
all existing kinds and missing resource families, native declarative fidelity,
defaults, reference/ownership boundaries and the operator's complete authoring
journey. Preserve useful existing shapes. Large public API changes require
owner approval of current/proposed examples before becoming the target;
small documentation corrections may proceed. This changes no implementation
authority.

### M2e

**Requires:** M2d. Deliver full-featured stretched Ceph for every desired-state
configuration and cluster size supported by the qualified IBM release,
subject to its topology, capacity and service compatibility requirements.
Reference profiles include two data sites and a third monitor-only arbiter;
their counts impose no product ceiling. **Exit:** X65/X66 and B488's accepted
emulated and physical fault/recovery, client-access and removal evidence for
the supported matrix. Service-specific larger profiles qualify features such
as NVMe-oF; unsupported combinations refuse with the provider requirement.

The submilestones proceed in order. M2c to M2e require the preceding
submilestone's accepted operator evidence. All retain M2's bootstrap and exact
continuation boundary; M2e does not authorize arbitrary unsupported input or
day-2 mutation. M2 completion includes M2a and all M2b to M2e gates.

## Journey and backlog review

B80 previously combined M2b to M2d and depended on physical
installation before a virtual cluster could run. It now owns core bootstrap;
the split items own service families and each acceptance tier. B81 keeps pools
and placement; its file, object, gateway and export portions have explicit
owners. B472 keeps definition and release qualification; B474 owns executable
projection evidence. These are splits, not a reduction in D128's coverage.

B82 moves to the parked backlog because it names no concrete extra OS variant.
B346 joins M2 to qualify the FIPS controller/key path used by the security
profile; this does not claim a certified controller runtime. B100 (external
load balancer), B107 (external Ceph), B330 (controller source adapter, closed
by X88) and B331 (controller FIPS runtime) stay parked: no matrix row requires those new
capabilities. B451's applicable host observations are part of B73/B305's
acceptance preparation; its unrelated research is not promoted. Shared later
milestone items are re-triaged only if a concrete Ceph consumer demonstrates
a blocker, without silently waiving that dependency.
Specifically, B472/B490 check [B237](m3.md#b237) and [B239](m3.md#b239) if
Ceph tooling uses controller target-client areas; B79 checks
[B251](m3.md#b251) against its adapter diagnostics. A confirmed shared blocker
is moved or split before that consumer is promoted, with its ID and evidence
preserved. Their current container-cluster remainder stays in M3.

The minimal profile does not wait for physical acceptance, bonded networking,
FIPS or root encryption. Full profiles still qualify every supported row.
Each profile is a fresh context or exact continuation of its own frozen
operation; these checkpoints do not authorize growing a completed apply.
Native topology restrictions and alternative profiles are recorded in the
[coverage requirements](../storage-coverage.md#stretch-constraints).

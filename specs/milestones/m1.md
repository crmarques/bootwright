pre-OpenShift readiness program the owner started on 2026-09-26, the 2026-09

## Item detail

### B17

Per-invocation private scratch passed to every role, disjoint machine and
provider namespaces and hardened delete guards, before lifecycle concurrency
rises above one. Every lifecycle role's owner shares the work. **Exit
evidence:** a two-concurrent-installs test; B39's no-fixed-scratch-path rule.

### B18

Bounded parallel block execution is delivered; what remains is the lock it
does not need but a reader does. A lifecycle operation holds the exclusive root
lock for its whole duration, so a concurrent read refuses; narrowing that to
the context lease alone would let a read such as `status` observe a running
operation. It needs [B17](#b17) and a cross-context concurrent-install test.
**Exit evidence:** concurrent-reader evidence for the narrowed lock, and proof
that an operation's own blocks still see one coherent record set.

### B19

One implementation of [the adapter result protocol](../architecture.md#the-adapter-result-protocol),
and one Ansible runner: a shared plugin base and one Go decoder over the
protocol table X11 delivered. Its hang clause landed as S14 in X14. Ten
per-capability action plugins each carry their own copy of the protocol's
phase dispatch, acknowledgement, group emission and postcondition rule, and
each is paired with a documentation-only module. Beside them,
`controller/ansiblelocal` is a second runner with a second protocol reader with
a different record bound and a `prepared` phase the lifecycle runner does not
have, so `setup` and the controller stage cross a different boundary from every
other block. A refusal that races the adapter's own non-zero exit can be
classified `failed` instead of `unknown`, and a controller refusal before
native authorization releases the adapter only at its next acknowledgement.
Collapsing both is mechanical but changes what every role emits and what fails
a run, and no in-tree gate proves an adapter's real host behavior. Postcondition
decisions stay in Go (D11); whether progress groups come from task tags through
a callback plugin instead of emission tasks changes what a role contains.
**Exit evidence:** one shared protocol implementation with its own unit tests;
one runner whose request, phases and failure semantics both consumers share;
per-capability evidence proved by its own tests; the collection sanity, lint
and integration gates; and a real-host apply and destroy before the old paths
are removed.

capability over one definition; collapsing them to one role changes each frozen

**Exit evidence:** one parameterized managed-service role with its argument
spec, the collection gates over it, and a real-host apply and destroy of one
managed service before the copies are removed.

### B23

killed supervisor leaving no worker.

### B24

### B29

Resolution gaps X18's S27 and its reviews left, most needing adapter changes;
Infrastructure services and Substrate share the work. An installation removal
killed while its package tree is deleted resolves completed, because the
inspect reports the tree only by its `.treeinfo` marker, which the deletion
removes first. An installation apply killed before it published anything
resolves unknown for ever, because the observe's absence form reports power
`''` where `ValidateNoEffect` requires `Off`. The installation and
agent-install removal observations run the whole apply observation (identity
channel, fleet SSH, BMC and `oc` reads) where content or media alone decide. A
physical agent-install removal selects the installed disk as boot device after
ejecting, which no evidence reports. A node presenting a foreign image leaves
an agent-install removal unknown although the removal ejects any node's media;
whether that reads as partial is an owner decision. A destroy over an
unfinished apply resolves the apply's blocks through `Observe`, which reads a
present managed service with a silent listener as unknown. **Exit evidence:**
protocol tests and a removal-observation row for each. Since X19 an unkept
boot-device selection fails the physical agent-install removal run, and an
unreadable media device leaves a removal observation unknown rather than
completed.

**Decided on 2026-09-30 (D27).** A node presenting a foreign image during an agent-install removal reads as partial when the node is one of this cluster's declared Machines, because the removal ejects any node's media and repeating it converges; it stays unknown only when the node cannot be read. The item's other resolution gaps keep their text.

### B41

Bring `file`-sourced Secret material under the
[copied-input rule](../project.md#design-priorities-and-non-goals) so
materialization reads only context custody. The
[file source](../api/secrets.md#file-source) names operator-owned paths that a
lifecycle operation reads at materialization, after admission; whether import
copies them into the keyring, the `secret` tree does, or the arm is retired
changes the Secrets API and custody contract. **Exit evidence:** a closed
import journey and record format, binding of imported bytes to the declaring
Secret, refusal of a changed or missing source after import, non-disclosure and
negative effect tests.

**Decided on 2026-09-30 (D36).** Compilation refuses `Secret.spec.source.file` in every type's shape. The refusal names the remedy: declare `contextStore: {}` and run `secret set --name <n>` with that type's file flags. The design priorities drop the recorded exception, and the Secrets, contexts and security specs drop their file-source rules. Binding, `secret check`, `secret show` and bounded machine commands read only keyring versions, so `secret set` is the only command that opens an operator path. Exit evidence: a compiler refusal test with its remedy for each file shape; custody tests showing that bind, check and show open no file for any source; and a removal test that still reopens an existing binding holding a version once read from a file.

### B42

One recovery for a registered operation whose frozen Secret binding can no
longer be reopened. A continuation reopens the exact binding the operation
froze, and so does a fresh removal of its apply since
[X9](delivered.md#x9--removal-under-the-build-in-hand), so a binding lost to an
earlier defect or to operator action leaves the context with no continue and
no destroy; only an orphan-acknowledged `context delete`
([X10](delivered.md#x10--orphan-acknowledged-context-delete)) leaves it, and
that abandons what it owns. Whether recovery re-binds under a proved-equivalent
declaration, admits a removal without the binding, or releases ownership
explicitly changes both contracts. Restated on 2026-09-28 after X6, X9 and X10.
**Exit evidence:** the exact recovery journey and its authorization, proof
that re-acquired material is the material the operation froze or an explicit
refusal, ownership and reservation release, and crash and replay tests over a
lost binding.

**Decided on 2026-09-30 (D37).** A continuation or fresh destroy whose operation names a binding that the keyring no longer lists refuses before it presents a plan, registers anything, or releases any reservation or binding. It gives one diagnostic in the B32 shape, naming the operation, the binding and the exits (restore the keyring from a complete backup, or `context delete --purge --allow-orphans` and then remove the named objects by hand). A binding that is still listed but whose material cannot be read refuses the same way when it is reopened. `status` names such an operation with that exit as its only next step, and the state reconciliation spec states that no re-binding, substitution or in-context release exists. Exit evidence: lifecycle journey tests for continue and destroy, over a deleted binding and over a bound version whose part is missing, showing that nothing registers, nothing is released and a retry refuses identically; a status golden for the state; and an orphan-acknowledged delete test over the same state.

### B43

One recovery for an operation whose unknown block no observation can resolve.
[Resolution](../state-reconciliation.md#attempts-and-unknown-outcomes) admits
only positive completion or positive no effect, and an unknown block starts no
retry, dependent block, destroy effect or replacement while
[deletion](../contexts.md#permanent-deletion) refuses a context that owns one
until the operator abandons it. A partially realized target proves neither
state (a libvirt domain defined and owned whose management controller never
started is the worked example), so the context has no continue and no destroy,
and its only delete abandons what that block may own. M1h and the removal of an unfinished apply
narrowed what reaches this four times over: a diagnosed adapter failure is
reported as `failed`, leaving only a lost or cancelled result; a fresh destroy
supersedes any apply that has not completed, so neither a repaired adapter nor
an interrupt strands the context; a resolution that proves a target is this
context's own and part way realized now fails its block, which the next attempt
converges; and a removal performs that resolution itself before it registers.
What remains is an observation that can prove neither: a foreign target of the
same name, or one that cannot be read at all. That block admits no removal
effect, because no evidence says what it owns, and the removal that tried to
prove it refuses having registered nothing. Whether a capability may prove a
third resolution or destroy is admitted over an unknown block changes the
safety contract; abandoning the context locally is already answered and
recovers nothing. It overlaps [B29](#b29). **Exit evidence:** the exact
recovery journey and its authorization; proof that no unproved effect is
repeated outside the capability's safe retry contract; ownership and
reservation release; crash and replay tests over a partially realized target;
and the refusal that still holds when an effect is genuinely unprovable.

**Decided on 2026-09-30 (D38).** An unknown block that no observation proves still refuses every effect, and the removal refusal and `status` name, for each such block, why it stayed unknown (a foreign object, named; an unreadable target, with its host or endpoint; a listener with no machine behind it) and the matching remedy. Once the operator removes the foreign object or restores the target, repeating the verb resolves the block and goes on. `context delete --allow-orphans` releases the deleted context's host reservations and reports them. Exit evidence: journey tests over a lost libvirt machine attempt (foreign domain, then removed, and the removal completes; silent host, then answering, and the removal goes on; still foreign, and the refusal holds with its reason), crash and replay tests over each resolution and over a partially realized target, and a delete test showing another context can then reserve the released keys.

### B45

The remainder of the upgrade journey. Planning a removal from the plan its
apply froze is delivered by
[removal under the build in hand](delivered.md#x9--removal-under-the-build-in-hand),
so a moved content digest, a request shape one version old and an edited
declaration no longer strand a context. Two parts remain. `destroy` admits no
stage or block scope, so a recovery removes every block the context owns
rather than the one whose digest moved. And an operation that must be continued rather than
superseded still runs under the automation digest it registered under, but not
from the bundle it registered with. The operation record freezes the
executable's version and commit and the automation digest, and no bundle,
setup catalog or resolved closure. A continuation runs whichever bundle the
current setup receipt names, and it refuses only when this executable's
automation digest, or that bundle's automation bytes, differ from what the
operation registered under; a bundle that moved to another native, Python or
Ansible closure under the same automation is used silently (found in X22).
Only a fresh verb runs under the build in hand. The execution section of
[state reconciliation](../state-reconciliation.md) says Go freezes each
implementation's pinned execution dependencies, which is not yet true: this
item makes it true, or the claim goes. **Exit
evidence:** the authorization and journey of a scoped removal, and proof that
a scope never leaves a dependent behind; how a continuation names the bundle
identity its frozen operation needs so the refusal states the remedy; proof
that a continuation detects a bundle that moved under the same automation; and
crash and replay tests over both.

**Decided on 2026-09-30 (D41).** B45 becomes: a continuation runs only under the execution closure it registered with. Registration records the bundle's resolved Python and Ansible closure identity in the operation record. Before a continuation of either verb restores its log or marks its operation running, it refuses `lifecycle.state` when the receipt's bundle carries another closure, naming the executable version and commit and the Python and ansible-core releases; the refusal for a changed automation digest names the executable too. A bundle republished only for a native re-solve continues. The spec's 'Not yet met' line goes, the native package closure is stated as host-owned, and scoped removal moves to the backlog. Exit evidence: lifecycle journey tests showing a moved closure refused with no effect and no record change, a native-only re-solve continuing, the refusal text, an earlier-version operation record refused with its remedy, and crash-replay of registration with the new field.

### B46

A durable home for what local `setup` prints. Setup allocates
[no lifecycle identity and no operation log](../cli/output.md#private-operation-logs),
so the Ansible that installs the container runtime and publishes the execution
bundle discards its own output, and a failure it does not diagnose leaves
nothing to read. The controller stage has no such gap, because it is a
lifecycle block whose attempt already owns a retained output file, and neither
does a bounded run, which retains its own under
[`state/runs/<run-id>`](../cli/output.md#bounded-run-output). Whether setup
gains a bounded log tree beside its
[private recovery receipt](../controller.md#publication-and-interrupted-setup),
reuses the receipt itself, or keeps discarding changes what a context-free
local command is permitted to leave behind. **Exit evidence:** a closed path
grammar, ownership and retention bound beneath the root-owned controller area;
exclusive creation that follows no link and overwrites no unrelated content;
proof that a retention fault never changes a setup outcome or its receipt; the
`Logs` reference in the human result; and negative tests over a full,
unwritable and pre-existing destination.

**Decided on 2026-09-30 (D42).** A confirmed `setup` that starts its controller Ansible, for a preparation or a recovery, first creates `/var/lib/bootwright/controller/runs/<run-id>/run.output` exclusively beneath the held controller directory handle. It never follows a link and never reuses an existing name. The file keeps that Ansible's standard output and error under the modes, 8 MiB limit and `no_log` masking of a bounded run's output. Run IDs are numbered `setup-000001` upward, and only the newest eight are kept: the oldest is removed before a new one is created. Human setup output names the run directory as `Logs` before the Ansible starts and after the result. A dry run, a no-op setup and the dependency helpers create nothing, and a creation, write or removal failure changes neither the outcome nor the receipt. Exit evidence: tests that a preparation and a recovery each keep their Ansible output; that a full area, an unwritable parent, an existing run name and a link in place of `runs` each leave the outcome and receipt byte-identical to a run without retention; that controller admission accepts `runs/` holding only well-formed run entries and refuses anything else; and a human golden showing both `Logs` lines, with the output, controller, contexts and controller-record specs amended.

### B111

A virtual node may declare a `wwn` root-device hint alone. Since X19 it
reaches the agent configuration, but the libvirt domain gives its disks no
WWN, so the hint can match no disk. Decide whether agent install refuses a
`wwn` hint on a virtual node or the domain carries one. **Exit evidence:** the
refusal or a domain test.

**Decided on 2026-09-30 (D44).** Validation refuses a Machine on a libvirt provider that declares a wwn, hctl or serialNumber root-device hint. The issue sits at that hint's path and says the disks this substrate creates carry no WWN, SCSI address or serial number. deviceName, minSizeGigabytes, model, vendor and rotational stay admitted, and a bare-metal Machine keeps every hint. The machines API spec states the refusal and the substrates spec states what a created disk presents. Exit evidence: an admission test refusing each of the three hints on a libvirt Machine and admitting them on a bare-metal one, and X19's every-hint agent-config test rewritten so it no longer runs the hints through a virtual node that admission refuses.

### B137

Since X26 `status` names each record contradiction, but its next steps still offer `plan` and `apply` beside records that make both refuse; and a failed destroy a retry left running reports its next step as a continuation, where the code replaces the destroy. Whether next steps leave out verbs that refuse changes what an operator sees. **Exit evidence:** status goldens over each state.

**Decided on 2026-09-30 (D31).** `status` offers a next step only where that verb's decision would pass over the records it read:

- over a lost index, nothing;
- over an incomplete apply, the continuation unless a lost record or an all-done failure refuses it, and the removal unless the listed contradictions refuse it;
- over an incomplete removal, its continuation unless a lost record refuses it.

A failed destroy reports `next: destroy` in status and in its own receipt, as plan's receipt already does. Status and plan derive `resolve` from the same rule. The cli spec states both.

**Exit evidence:** a lifecycle table test over each record state (lost index, lost record, failed apply all done, dependency contradiction, failed apply that started nothing, running destroy with a lost record, failed destroy). CLI status goldens in human and JSON form for a contradicted context.

### B140

X26 derived the agent-install node margin from the Redfish client's documented bounds, but no test holds its composition to the calls the install role makes per node, so a call added there does not grow the margin. **Decided on 2026-09-30 (D32).** The install request freezes a boot budget of 300 seconds per node, never less than 900, so a cluster of up to three nodes plans as it does today. ### B143

The physical-machine evidence path trims and bounds the reported UUID and serial but does not refuse control characters, so a pin can carry them into later operations; only the power refusal's display is sanitized since X26. Stripping control characters also leaves Unicode format characters such as bidi overrides. **Exit evidence:** evidence tests with control and format characters.

**Decided on 2026-09-30 (D34).** The bare-metal evidence path and Go's evidence decoder refuse a reported UUID or serial that, after trimming surrounding space, is longer than 128 characters or contains any character that is not printable (Go unicode.IsPrint, Python str.isprintable). ### B146

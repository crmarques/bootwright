# M1 — Foundations

Deliver substrates, infrastructure services and Machines: provider and
machine realization, operating-system installation, shared service lifecycles,
identity, access, power, continuation and safe removal. The owning contracts
are [substrates](../substrates.md), [managed OS](../managed-os.md) and
[infrastructure services](../infrastructure-services.md).

[D158](backlog.md#d158) redefines M1 on 2026-10-17 and reopens it for the
shared work below. The former hardening scope remains accepted under
[D156](backlog.md#d156) and
[X98](delivered.md#x98--m1-owner-acceptance); its dated completion and evidence
are preserved in the [historical baseline](#accepted-hardening-baseline).
This regrouping implements no capability and creates no new acceptance claim.

[X103](delivered.md#x103--audit-defects-and-d163-screens-for-foundations-m1)
delivered the general Foundations defects of the 2026-10-18 audit and the D163
screens ([D163](backlog.md#d163)).

[X156](delivered.md#x156--go-toolchain-vulnerability-gate-go12610) moved
the Go toolchain to go1.26.10, which clears GO-2026-6809 in `make vulncheck`.

**Requires:** none as a whole; each submilestone's Requires cell names its
prerequisites and each arm its declared host and shared contracts. **Exit tier:** in-tree boundary/failure/replay tests and
owner-accepted provider-specific lifecycle runs; M1e requires real hardware
and independent erase proof. M1f/M1g fix their exact qualification profiles
before promotion. **Open decisions:** the existing item-level definition and
safety gates below, Registry's implementation and the two future adapters.

### B75

The FIPS profile arm, with its secret-free or private publication. **Exit
evidence:** renderer and executor parity and a qualified FIPS install.

Target FIPS covers the installed OS boot state, crypto policy, SSH keys and
OS packages, with a reboot proof. CephX keys and Ceph daemon/service
compatibility remain M2 qualification under B472, B484 and B485.
It is distinct from controller cryptographic certification. Each incompatible
key/service refuses before installation; B346 qualifies controller access.

**Delivered in-tree (X60):** a profile enabling `fips` is admitted on a virtual
Machine, appends `fips=1` once, installs an ECDSA P-256 guest-agent host key,
refuses an Ed25519 or short RSA fleet key before registration (also when the
key is bound), proves `/proc/sys/crypto/fips_enabled` and the crypto policy
after network convergence and refuses `fips-not-enabled` otherwise; an
observation reads the same proof. Its evidence is offline: renderer and
executor parity, the refusal-table rows, the Ansible unit tests and the
architecture suite. **Acceptance baseline:** `d129085a1835bd09618b79ac3d1342085b631709`.
**Remaining (owner's live row):** a FIPS install and reboot on a virtual
Machine that proves the boot state, crypto policy and host-key access on the
installed system, with an owner-accepted ledger row. Ceph on a FIPS-mode host
stays [B484](m2.md#b484)'s.

### Controller setup v2

**Why.** The owner's request of 2026-10-14 (D152): setup took more than three
minutes even after an earlier build's setup, and Fedora 43 to 44 broke it.
Today setup resolves and installs a private CPython, ansible-core and a frozen
controller DNF plan into a per-build bundle area of about 190 MB, guarded by
byte digests of glibc and libgcc, so any build or OS update repeats most of it.

**Design.** Setup installs two things, and only when they are missing.
Host packages are asked of the host's own dnf by name or RPM capability, with
a verbatim `--assumeno` preview shown before confirmation. One venv on the OS
CPython 3.12 to 3.14 (`/usr/bin/python3.X`) receives the wheels of a hash lock
each build embeds, installed by pip with `--no-index --no-deps
--require-hashes` from a content-addressed wheel cache. The automation stays in
the binary and is unpacked into root-owned staging for each Ansible launch, so
the runtime's identity is the lock digest, the Python ABI and the interpreter
path, and a live operation's closure is the lock digest and the ABI: an
`ansible/`-only fix or any rebuild with the same lock needs no setup and
continues a live operation. Setup state moves to a setup-owned subtree,
`/var/lib/bootwright/setup/` (state, lock, runtimes, wheel cache, run logs),
whose format heals itself. The cut-over bumps the registry to version 6 and the
controller record to version 3 and refuses an earlier store with the
fresh-install remedy. D152's clauses hold every choice and what was declined.

**Targets** (the owner measures before in X87's S0 and after in X90's
acceptance): a fresh setup within 60 s excluding dnf, the ready path within
2 s, a new build with the same lock within 2 s, and a runtime of at most 60 MB
and 3,000 files.

commit on local main.

# M1 — Hardening

Security, code and architecture improvement, and bug fixes. M1 holds the
pre-OpenShift readiness program the owner started on 2026-09-26, the 2026-09
audit follow-ups, and the safety, recovery and operability items that serve no
single product milestone. The [product scope](../project.md#product-scope)
names no platform for it; it serves the
[design priorities](../project.md#design-priorities-and-non-goals) of least
privilege and fail-closed effects.

**Requires:** none. **Exit tier:** in-tree, plus the real-host run of
[B49](#b49). **Open decisions:** those the Requires cells of B29, B34 and B40
name.

Slices X11 to [X18](delivered.md#x18--durable-records) delivered toward it and
keep their own IDs in [delivered](delivered.md).

## Item detail

### B5

The substrate machine port (pre-boot proof, boot media, identity read, power)
as argument-spec entry points, with every consumer booting through the
substrate-owned boot operation instead of selecting a boot device itself (D1).
Since X19 every Redfish read discovers media first, so until this item gives
power-only readers a read without media discovery, one failed read ends the
managed-OS installer wait and the libvirt controller-verification poll. The
read-only consumers also move off the mutating boot module here, and a changed
identity inspection keeps its UUID and serial, empty when the system read
fails. **Exit evidence:** a collection structural test that consumers include
only the port's entry points.

### B6

Freeze each node's hardware from `substrate.TargetFor`, include the substrate's
`pre_boot.yml` before `insert` and end every arm in a terminal fail. The
pre-boot proof compares the UUID and serial
[X19](delivered.md#x19--redfish-and-identity) pins from the Machine's
bare-metal block (D6), in both consumers of the bare-metal `pre_boot.yml`: the
managed-OS installation and the cluster boot. That needs an execution to
receive the evidence its dependency block proved in the same operation, which
the lifecycle's execution does not carry today, and the pin reaches the role
encoded, never as raw template input. Until then the bare-metal pre-boot proof
requires only a non-empty UUID or serial. Lifting [B61](m3.md#b61)'s physical-node
refusal is [B67](m3.md#b67). **Exit
evidence:** `./scripts/go test ./internal/containercluster/...`; B7's
insert-after-pre-boot rule.

### B7

The structural rules for substrate dispatch, each with the fix it guards: every
substrate dispatch ends in a terminal `fail` (today the consumers refuse an
unknown arm with a leading assert), and an insert is preceded by a pre-boot
proof ([B6](#b6)). The module's other rules are [B39](#b39). **Exit
evidence:** `./scripts/ansible-check --suite units`.

### B8

The observation reports whether the hypervisor answered; absence evidence
publishes observed values and checks sockets are free. X16 delivered its
quiescence half and left two pre-existing gaps here: the Evidence paragraph of
[substrates](../substrates.md) says the inverse forces the domain off, which it
never does, and `observe.yml` reads empty domain and unit as removed, so a
machine with only its disks left resolves unknown instead of partial. X18's
removal resolution depends on the same fixes: a disk whose `qemu-img info`
fails reads absent, and the host absence form proves neither that the
hypervisor answered nor that the pool directory is gone, so a host removal
interrupted after its effect is repeated once ([substrates](../substrates.md)
records the host case as Not yet met). **Exit evidence:** a Go quiescence
table; `./scripts/ansible-check --suite units`.

### B9

The trust half of the physical installation path (D3): the BMC certificate is
imported where the BMC supports it, otherwise an explicit per-machine
`disable-verification` exception applies, never a default, and is refused for
private consumers unless [security](../security.md) records a bounded
exception; controller-to-BMC TLS gains a CA-bundle field. X14 delivered its
serving half as S17 (serving-uid ownership and a fetch-through probe). The
physical installation refusal of [B73](m4.md#b73) is lifted by that item's own
host-key repair, built on this one. Substrate admission's `Validate` is at the
100-line limit since X22, so this item adds its checks in a named helper. **Exit evidence:** tests that import a BMC
certificate into the controller-to-BMC CA bundle and verify against it, refuse
`disable-verification` for a private consumer, and admit the per-machine
exception only where it is declared.

### B10

The administrator-access custody contract descoped from [B61](m3.md#b61): the
access a completed installation leaves in the installer's root-owned work area
moves into context custody, which `cluster kubeconfig` reveals (D4), and a
destroy never deletes the only access, as the program planned X21 on
2026-09-26. X16 found two hazards custody removes: each
rerun of `agent wait-for install-complete` prepends the router CA to
`auth/kubeconfig` again, growing it toward the inspection's 64 KiB read bound,
and a budget kill during the installer's in-place write of that file could
truncate it. **Exit evidence:** the custody contract's own non-disclosure and
removal tests, and a complete `cluster kubeconfig` journey with diagnostics,
which also meets the cluster access evidence of [B101](backlog.md#b101).

### B17

Per-invocation private scratch passed to every role, disjoint machine and
provider namespaces and hardened delete guards, before lifecycle concurrency

### B18

Bounded parallel block execution is delivered; what remains is the lock it
does not need but a reader does. A lifecycle operation holds the exclusive root
lock for its whole duration, so a concurrent read refuses; narrowing that to
the context lease alone would let a read such as `status` observe a running
operation. It needs [B17](#b17) and a cross-context concurrent-install test.
**Exit evidence:** concurrent-reader evidence for the narrowed lock, and proof
that an operation's own blocks still see one coherent record set.

### B19

One implementation of [the adapter result protocol](../architecture.md#the-adapter-result-protocol),
and one Ansible runner: a shared plugin base and one Go decoder over the
protocol table X11 delivered. Its hang clause landed as S14 in X14. Ten
per-capability action plugins each carry their own copy of the protocol's
phase dispatch, acknowledgement, group emission and postcondition rule, and
each is paired with a documentation-only module. Beside them,
`controller/ansiblelocal` is a second runner with a second protocol reader with
a different record bound and a `prepared` phase the lifecycle runner does not
have, so `setup` and the controller stage cross a different boundary from every
other block. A refusal that races the adapter's own non-zero exit can be
classified `failed` instead of `unknown`, and a controller refusal before
native authorization releases the adapter only at its next acknowledgement.
Collapsing both is mechanical but changes what every role emits and what fails
a run, and no in-tree gate proves an adapter's real host behavior. Postcondition
decisions stay in Go (D11); whether progress groups come from task tags through
a callback plugin instead of emission tasks changes what a role contains.
**Exit evidence:** one shared protocol implementation with its own unit tests;
one runner whose request, phases and failure semantics both consumers share;
per-capability evidence proved by its own tests; the collection sanity, lint
and integration gates; and a real-host apply and destroy before the old paths
are removed.

### B26

A keyring initialization killed inside any of its staged writes resumes:
initialization recovery treats a root `secrets/pending-*` stage that decodes as
no record as an interrupted temporary, and the cleanup after publication
removes it. Today the kill leaves a stage the keyring refuses with
`secret.store.corrupt`, so neither `context init` nor `secret encryption init`
completes. Split from S8 on the owner's choice of 2026-09-28; since X18 an
in-process interruption leaves no such stage. **Exit evidence:** the contextfs

write.

### B27

The lost and lagging record paths X18 left, found by its items and reviews. A
lost `index.json` reads as no operation, so a fresh apply registers beside
directories that hold block records and a destroy over pristine evidence
settles over them. A completed destroy whose plan holds a block that is not
`done` settles and is never finalized. A failed removal whose blocks are all
`done`, which a removal of it killed right after its resolution leaves, is
finalized by no verb and refused by every destroy (the fix: finalize it under
destroy as X18 does an unknown one, and correct the spec's claim that a failed
removal holds the block that failed). A dependency rewritten to `failed`,
`running` or `unknown` while a dependent started escapes rule (a), and a
`running` block masks rule (c) beside a lost failed-block directory. Records
written before `83dcbebe` leave a first start as an attempt beside no block
record, which a removal now refuses and a continuation already refused. A
continuation over a started block's lost record marks the operation running
before `StartAttempt` refuses. The refusals point at `bootwright status`, which
shows neither the contradiction, unindexed directories nor unexpected evidence.
The spec's Operation records say a block record carries its next attempt
number, where it counts the attempts started, and its Block transitions say an
attempt that cannot start leaves its block record unchanged, where a start
whose final publication lands and then errors leaves it `running`. **Exit
evidence:** journeys over each path that refuse or converge; `status` naming
what each refusal names.

### B28

What X18's evidence and claim rules leave. Every fresh apply refused after its
claim leaves an empty operation directory nothing removes, counting toward
`MaxOperations` (4096) and the operation area's entry bound, so enough refused
retries stop even a destroy from registering. A bounded run's transient
binding read in a registration's listing before its reopen can be collected,
failing that run once, because a binding names no consumer (a keyring format
change). A destroy over pristine evidence with no reservation settles beside a
stranded binding, which only the next registration collects. A destroy
interrupted after its operation reads `done` leaves its releases and pristine
publication to the next destroy. **Exit evidence:** a reclaim test for empty
claims; a bounded-run race test.

### B29

Resolution gaps X18's S27 and its reviews left, most needing adapter changes;
Infrastructure services and Substrate share the work. An installation removal
killed while its package tree is deleted resolves completed, because the
inspect reports the tree only by its `.treeinfo` marker, which the deletion
removes first. An installation apply killed before it published anything
resolves unknown for ever, because the observe's absence form reports power
`''` where `ValidateNoEffect` requires `Off`. The installation and
agent-install removal observations run the whole apply observation (identity
channel, fleet SSH, BMC and `oc` reads) where content or media alone decide. A
physical agent-install removal selects the installed disk as boot device after
ejecting, which no evidence reports. A node presenting a foreign image leaves
an agent-install removal unknown although the removal ejects any node's media;
whether that reads as partial is an owner decision. A destroy over an
unfinished apply resolves the apply's blocks through `Observe`, which reads a
present managed service with a silent listener as unknown. **Exit evidence:**
protocol tests and a removal-observation row for each. Since X19 an unkept
boot-device selection fails the physical agent-install removal run, and an
unreadable media device leaves a removal observation unknown rather than
completed.

froze, and so does a fresh removal of its apply since
[X9](delivered.md#x9--removal-under-the-build-in-hand), so a binding lost to an
earlier defect or to operator action leaves the context with no continue and
no destroy; only an orphan-acknowledged `context delete`
([X10](delivered.md#x10--orphan-acknowledged-context-delete)) leaves it, and
that abandons what it owns. Whether recovery re-binds under a proved-equivalent
declaration, admits a removal without the binding, or releases ownership
explicitly changes both contracts. Restated on 2026-09-28 after X6, X9 and X10.
**Exit evidence:** the exact recovery journey and its authorization, proof
that re-acquired material is the material the operation froze or an explicit
refusal, ownership and reservation release, and crash and replay tests over a
lost binding.

### B43

One recovery for an operation whose unknown block no observation can resolve.
[Resolution](../state-reconciliation.md#attempts-and-unknown-outcomes) admits
only positive completion or positive no effect, and an unknown block starts no
retry, dependent block, destroy effect or replacement while
[deletion](../contexts.md#permanent-deletion) refuses a context that owns one
until the operator abandons it. A partially realized target proves neither
state (a libvirt domain defined and owned whose management controller never
started is the worked example), so the context has no continue and no destroy,
and its only delete abandons what that block may own. M1h and the removal of an unfinished apply
narrowed what reaches this four times over: a diagnosed adapter failure is
reported as `failed`, leaving only a lost or cancelled result; a fresh destroy
supersedes any apply that has not completed, so neither a repaired adapter nor
an interrupt strands the context; a resolution that proves a target is this
context's own and part way realized now fails its block, which the next attempt
converges; and a removal performs that resolution itself before it registers.
What remains is an observation that can prove neither: a foreign target of the
same name, or one that cannot be read at all. That block admits no removal
effect, because no evidence says what it owns, and the removal that tried to
prove it refuses having registered nothing. Whether a capability may prove a
third resolution or destroy is admitted over an unknown block changes the
safety contract; abandoning the context locally is already answered and
recovers nothing. It overlaps [B29](#b29). **Exit evidence:** the exact
recovery journey and its authorization; proof that no unproved effect is
repeated outside the capability's safe retry contract; ownership and
reservation release; crash and replay tests over a partially realized target;
and the refusal that still holds when an effect is genuinely unprovable.

### B44

The automation projection as its own layer over a shared bundle foundation.
Retiring a superseded execution bundle is delivered by
[`setup --purge-old-bundles`](../controller.md#supported-host-and-dependency-selection)
(X7). What remains: an automation-only revision still names a whole new bundle
area and republishes the same closure into it, because the projection that
carries the automation is part of the bundle's identity rather than a layer
over a shared foundation. **Exit evidence:** closed layer identities and their
attribution; proof that a foundation is reused only when its resolved closure
is unchanged and that sealed-bundle immutability survives an automation-only
revision; and bounded reacquisition.

### B45

The remainder of the upgrade journey. Planning a removal from the plan its
apply froze is delivered by
[removal under the build in hand](delivered.md#x9--removal-under-the-build-in-hand),
so a moved content digest, a request shape one version old and an edited
declaration no longer strand a context. Two parts remain. `destroy` admits no
stage or block scope, so a recovery removes every block the context owns
rather than the one whose digest moved. And a sealed bundle is retired by
nothing ([B44](#b44)), so an operation that must be continued rather than
superseded still runs under the automation digest it registered under, but not
from the bundle it registered with. The operation record freezes the
executable's version and commit and the automation digest, and no bundle,
setup catalog or resolved closure. A continuation runs whichever bundle the
current setup receipt names, and it refuses only when this executable's
automation digest, or that bundle's automation bytes, differ from what the
operation registered under; a bundle that moved to another native, Python or
Ansible closure under the same automation is used silently (found in X22).
Only a fresh verb runs under the build in hand. The execution section of
[state reconciliation](../state-reconciliation.md) says Go freezes each
implementation's pinned execution dependencies, which is not yet true: this
item makes it true, or the claim goes. **Exit
evidence:** the authorization and journey of a scoped removal, and proof that
a scope never leaves a dependent behind; how a continuation names the bundle
identity its frozen operation needs so the refusal states the remedy; proof
that a continuation detects a bundle that moved under the same automation; and
crash and replay tests over both.

### B46

A durable home for what local `setup` prints. Setup allocates

nothing to read. The controller stage has no such gap, because it is a
lifecycle block whose attempt already owns a retained output file, and neither
does a bounded run, which retains its own under
[`state/runs/<run-id>`](../cli/output.md#bounded-run-output). Whether setup
gains a bounded log tree beside its
[private recovery receipt](../controller.md#publication-and-interrupted-setup),
reuses the receipt itself, or keeps discarding changes what a context-free
local command is permitted to leave behind. **Exit evidence:** a closed path
grammar, ownership and retention bound beneath the root-owned controller area;
exclusive creation that follows no link and overwrites no unrelated content;
proof that a retention fault never changes a setup outcome or its receipt; the
`Logs` reference in the human result; and negative tests over a full,
unwritable and pre-existing destination.

### B108

Since X19 the Redfish boot module states its worst cases: an insert may spend
at most 1,880 s in pauses and attach timeouts (10,940 s when every request
times out), an eject polls up to 24 times 5 s, and each state read makes up to
four requests of at most 30 s each. They exceed the cluster boot phase's
900-second budget, the five-minute node margin of the agent-install catalog and
the managed-OS media margin's assumptions. The boot task's wall-clock bound
fails closed with its hint, but the budgets and the client's bounds should
agree. **Exit evidence:** each margin derived from the client's documented
worst cases, with a test that holds them together.

### B109

A block completed by resolution reads back differently from one its attempt
completed. The lifecycle's evidence read returns only the last attempt's
evidence, so a block a resolution completed after an unknown or failed attempt
reads back null: its bare-metal identity pins nothing (X19's pin) and `machine
rsh` finds no host key for an installation resolved that way. And the operation
store records `changed` for every completed resolution, whatever the adapter
published, so a proving bare-metal apply resolved by observation reports a
change. **Exit evidence:** journeys where a resolved block's evidence and
outcome read back as the adapter proved them.

### B110

# M1 — Hardening

Security, code and architecture improvement, and bug fixes. M1 holds the
pre-OpenShift readiness program the owner started on 2026-09-26, the 2026-09
audit follow-ups, and the safety, recovery and operability items that serve no
single product milestone. The [product scope](../project.md#product-scope)
names no platform for it; it serves the
[design priorities](../project.md#design-priorities-and-non-goals) of least
privilege and fail-closed effects.

**Requires:** none. **Exit tier:** in-tree, plus the real-host run of
[B49](#b49). **Open decisions:** those the Requires cells of B29, B34 and B40
name.

Slices X11 to [X18](delivered.md#x18--durable-records) delivered toward it and
keep their own IDs in [delivered](delivered.md).

## Item detail

### B1

Redfish effects go through the vendor-neutral client: media discovery, transfer
protocol, task polling, `If-Match` and read-back. **Exit evidence:** three
firmware-shape fixtures.

### B2

A bare-metal replay reports unchanged. **Exit evidence:** a replay test.

### B3

Pin the first proved UUID and serial of a Machine and refuse a mismatch (D6).
**Exit evidence:** an identity-mismatch refusal test.

### B4

Every admitted root-device hint reaches the installer, and a hint set it cannot
carry refuses. **Exit evidence:** projection goldens and refusal tests.

### B5

The substrate machine port (pre-boot proof, boot media, identity read, power)
as argument-spec entry points, with every consumer booting through the
substrate-owned boot operation instead of selecting a boot device itself (D1).
**Exit evidence:** a collection structural test that consumers include only the
port's entry points.

### B6

Freeze each node's hardware from `substrate.TargetFor`, include the substrate's
`pre_boot.yml` before `insert` and end every arm in a terminal fail. Lifting
[B61](m3.md#b61)'s physical-node refusal is [B67](m3.md#b67). **Exit
evidence:** `./scripts/go test ./internal/containercluster/...`; B7's
insert-after-pre-boot rule.

### B7

The structural rules for substrate dispatch, each with the fix it guards: every
substrate dispatch ends in a terminal `fail` (today the consumers refuse an
unknown arm with a leading assert), and an insert is preceded by a pre-boot
proof ([B6](#b6)). The module's other rules are [B39](#b39). **Exit
evidence:** `./scripts/ansible-check --suite units`.

### B8

The observation reports whether the hypervisor answered; absence evidence
publishes observed values and checks sockets are free. X16 delivered its
quiescence half and left two pre-existing gaps here: the Evidence paragraph of
[substrates](../substrates.md) says the inverse forces the domain off, which it
never does, and `observe.yml` reads empty domain and unit as removed, so a
machine with only its disks left resolves unknown instead of partial. X18's
removal resolution depends on the same fixes: a disk whose `qemu-img info`
fails reads absent, and the host absence form proves neither that the
hypervisor answered nor that the pool directory is gone, so a host removal
interrupted after its effect is repeated once ([substrates](../substrates.md)
records the host case as Not yet met). **Exit evidence:** a Go quiescence
table; `./scripts/ansible-check --suite units`.

### B9

The trust half of the physical installation path (D3): the BMC certificate is
imported where the BMC supports it, otherwise an explicit per-machine
`disable-verification` exception applies, never a default, and is refused for
private consumers unless [security](../security.md) records a bounded
exception; controller-to-BMC TLS gains a CA-bundle field. X14 delivered its
serving half as S17 (serving-uid ownership and a fetch-through probe). The
physical installation refusal of [B73](m4.md#b73) is lifted by that item's own
host-key repair, built on this one. **Exit evidence:** tests that import a BMC
certificate into the controller-to-BMC CA bundle and verify against it, refuse
`disable-verification` for a private consumer, and admit the per-machine
exception only where it is declared.

### B10

The administrator-access custody contract descoped from [B61](m3.md#b61): the
access a completed installation leaves in the installer's root-owned work area
moves into context custody, which `cluster kubeconfig` reveals (D4), and a
destroy never deletes the only access, as the program planned X21 on
2026-09-26. X16 found two hazards custody removes: each
rerun of `agent wait-for install-complete` prepends the router CA to
`auth/kubeconfig` again, growing it toward the inspection's 64 KiB read bound,
and a budget kill during the installer's in-place write of that file could
truncate it. **Exit evidence:** the custody contract's own non-disclosure and
removal tests, and a complete `cluster kubeconfig` journey with diagnostics,
which also meets the cluster access evidence of [B101](backlog.md#b101).

### B11

CLI-owned tagged JSON DTOs, a JSON mode with a no-op progress reporter, and
every next step rendered. X17 found that `secret check` and `secret list` JSON
drop each secret's sequence ordinal (always 0) although the output spec
requires it, and that human `status` omits `context.mode`, `desired`, cluster
and storage cluster rows, `secrets` and the lifecycle `operation`, `verb` and
`state`, and shows only the first next step, although it must present the JSON
membership; the goldens pin today's bytes. X18 found that a settled verb that
first completed an interrupted finalization, or a destroy that released what an
interrupted registration left, still says only that nothing was left to do
([cli](../cli.md) records it as Not yet met). **Exit evidence:** exact JSON and
text goldens.

### B17

Per-invocation private scratch passed to every role, disjoint machine and
provider namespaces and hardened delete guards, before lifecycle concurrency
rises above one. Every lifecycle role's owner shares the work. **Exit
evidence:** a two-concurrent-installs test; B39's no-fixed-scratch-path rule.

### B18

Bounded parallel block execution is delivered; what remains is the lock it
does not need but a reader does. A lifecycle operation holds the exclusive root
lock for its whole duration, so a concurrent read refuses; narrowing that to
the context lease alone would let a read such as `status` observe a running
operation. It needs [B17](#b17) and a cross-context concurrent-install test.
**Exit evidence:** concurrent-reader evidence for the narrowed lock, and proof
that an operation's own blocks still see one coherent record set.

### B19

One implementation of [the adapter result protocol](../architecture.md#the-adapter-result-protocol),
and one Ansible runner: a shared plugin base and one Go decoder over the
protocol table X11 delivered. Its hang clause landed as S14 in X14. Ten
per-capability action plugins each carry their own copy of the protocol's
phase dispatch, acknowledgement, group emission and postcondition rule, and
each is paired with a documentation-only module. Beside them,
`controller/ansiblelocal` is a second runner with a second protocol reader with
a different record bound and a `prepared` phase the lifecycle runner does not
have, so `setup` and the controller stage cross a different boundary from every
other block. A refusal that races the adapter's own non-zero exit can be
classified `failed` instead of `unknown`, and a controller refusal before
native authorization releases the adapter only at its next acknowledgement.
Collapsing both is mechanical but changes what every role emits and what fails
a run, and no in-tree gate proves an adapter's real host behavior. Postcondition
decisions stay in Go (D11); whether progress groups come from task tags through
a callback plugin instead of emission tasks changes what a role contains.
**Exit evidence:** one shared protocol implementation with its own unit tests;
one runner whose request, phases and failure semantics both consumers share;
per-capability evidence proved by its own tests; the collection sanity, lint
and integration gates; and a real-host apply and destroy before the old paths
are removed.

### B26

### B27

The lost and lagging record paths X18 left, found by its items and reviews. A
lost `index.json` reads as no operation, so a fresh apply registers beside
directories that hold block records and a destroy over pristine evidence
settles over them. A completed destroy whose plan holds a block that is not
`done` settles and is never finalized. A failed removal whose blocks are all
`done`, which a removal of it killed right after its resolution leaves, is
finalized by no verb and refused by every destroy (the fix: finalize it under
destroy as X18 does an unknown one, and correct the spec's claim that a failed
removal holds the block that failed). A dependency rewritten to `failed`,
`running` or `unknown` while a dependent started escapes rule (a), and a
`running` block masks rule (c) beside a lost failed-block directory. Records
written before `83dcbebe` leave a first start as an attempt beside no block
record, which a removal now refuses and a continuation already refused. A
continuation over a started block's lost record marks the operation running
before `StartAttempt` refuses. The refusals point at `bootwright status`, which
shows neither the contradiction, unindexed directories nor unexpected evidence.
The spec's Operation records say a block record carries its next attempt
number, where it counts the attempts started, and its Block transitions say an
attempt that cannot start leaves its block record unchanged, where a start
whose final publication lands and then errors leaves it `running`. **Exit
evidence:** journeys over each path that refuse or converge; `status` naming
what each refusal names.

### B43

One recovery for an operation whose unknown block no observation can resolve.
[Resolution](../state-reconciliation.md#attempts-and-unknown-outcomes) admits
only positive completion or positive no effect, and an unknown block starts no
retry, dependent block, destroy effect or replacement while
[deletion](../contexts.md#permanent-deletion) refuses a context that owns one
until the operator abandons it. A partially realized target proves neither
state (a libvirt domain defined and owned whose management controller never
started is the worked example), so the context has no continue and no destroy,
and its only delete abandons what that block may own. M1h and the removal of an unfinished apply
narrowed what reaches this four times over: a diagnosed adapter failure is
reported as `failed`, leaving only a lost or cancelled result; a fresh destroy
supersedes any apply that has not completed, so neither a repaired adapter nor
an interrupt strands the context; a resolution that proves a target is this
context's own and part way realized now fails its block, which the next attempt
converges; and a removal performs that resolution itself before it registers.
What remains is an observation that can prove neither: a foreign target of the
same name, or one that cannot be read at all. That block admits no removal
effect, because no evidence says what it owns, and the removal that tried to
prove it refuses having registered nothing. Whether a capability may prove a
third resolution or destroy is admitted over an unknown block changes the
safety contract; abandoning the context locally is already answered and
recovers nothing. It overlaps [B29](#b29). **Exit evidence:** the exact
recovery journey and its authorization; proof that no unproved effect is
repeated outside the capability's safe retry contract; ownership and
reservation release; crash and replay tests over a partially realized target;
and the refusal that still holds when an effect is genuinely unprovable.

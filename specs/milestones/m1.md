### Controller setup v2

**Why.** The owner's request of 2026-10-14 (D152): setup took more than three
minutes even after an earlier build's setup, and Fedora 43 to 44 broke it.
Today setup resolves and installs a private CPython, ansible-core and a frozen
controller DNF plan into a per-build bundle area of about 190 MB, guarded by
byte digests of glibc and libgcc, so any build or OS update repeats most of it.

**Design.** Setup installs two things, and only when they are missing.
Host packages are asked of the host's own dnf by name or RPM capability, with
a verbatim `--assumeno` preview shown before confirmation. One venv on the OS
CPython 3.12 to 3.14 (`/usr/bin/python3.X`) receives the wheels of a hash lock
each build embeds, installed by pip with `--no-index --no-deps
--require-hashes` from a content-addressed wheel cache. The automation stays in
the binary and is unpacked into root-owned staging for each Ansible launch, so
the runtime's identity is the lock digest, the Python ABI and the interpreter
path, and a live operation's closure is the lock digest and the ABI: an
`ansible/`-only fix or any rebuild with the same lock needs no setup and
continues a live operation. Setup state moves to a setup-owned subtree,
`/var/lib/bootwright/setup/` (state, lock, runtimes, wheel cache, run logs),
whose format heals itself. The cut-over bumps the registry to version 6 and the
controller record to version 3 and refuses an earlier store with the
fresh-install remedy. D152's clauses hold every choice and what was declined.

**Targets** (the owner measures before in X87's S0 and after in X90's
acceptance): a fresh setup within 60 s excluding dnf, the ready path within
2 s, a new build with the same lock within 2 s, and a runtime of at most 60 MB
and 3,000 files.

**Plan.** Each step is one gate-passing commit; each slice is squashed to one
commit on local main.

- **X87, foundations,** is
  [delivered](delivered.md#x87--controller-setup-v2-foundations): additive
  and unwired, so behavior is unchanged except B548. B549 and B552 remained open

  X87's `890ba11c7` both refused `setup` on the owner's Fedora 44 host with
  `controller.setup` ("bootstrap publisher returned an unapproved
  response") in under a second, because all eight retained definitions were
  Fedora 43, so neither a ready path nor a new-build path existed to time.
  The bundle area held 1,920,036,538 bytes in 43,729 files (Python 3.14.7,
  ansible-core 2.21.4).
- **X88, the cut-over,** is
  [delivered](delivered.md#x88--controller-setup-v2-cut-over) on main after
  the owner deferred D152's clause 9 choice on 2026-10-14; D154 chose its

  Before any X88 build runs on the owner's host, the owner retires the live

### B466

**Implementation:** delivered in-tree by

Before X48, production nevertheless passed `Concurrency: 1` in

`TestLifecycleConcurrencyBound` enforced it pending B303 and B304. A second,

`Request.ExclusiveKeys` froze the shared package-tree path on each entire

### B608

Found in the owner's three-node run of 2026-10-15
([X93](delivered.md#x93--the-owner-run-of-2026-10-14)). The libvirt host role defines each managed guest
network with `<bridge zone="trusted">`
(`ansible/collections/ansible_collections/bootwright/core/roles/substrate_libvirt_host/templates/network.xml.j2`,
`NETWORK_BRIDGE` in `plugins/module_utils/substrate_libvirt.py`), and libvirt
refuses to start a network that names a firewalld zone while firewalld does
not report itself running. At boot, systemd marks firewalld active once it
holds its D-Bus name, before firewalld has loaded its configuration, so
`virtnetworkd`'s autostart can run inside that window. The network stayed
inactive and its bridge absent while the domains, media pool and managed
services returned; guest power-on then failed with `lifecycle.state`.
Ordering `virtnetworkd` after `firewalld.service` alone cannot prove actual
firewall readiness.

**Outcome:** a managed network starts after every host restart. The network
XML retains `zone="trusted"`; an owned per-provider oneshot readiness unit
orders actual firewalld readiness before libvirt network autostart. The
[Substrates firewall-readiness contract](../substrates.md#provider-host-realization)
owns the bounded probe, exact unit/link ownership, current-apply check,
external-only exclusion and completion/removal evidence. The earlier proposed
permanent-only bridge binding is replaced: libvirt selects its default zone
when XML omits one and repeats that selection after firewall reloads. X96
delivers this correction with `substrate-host-libvirt-v5` and a new automation
digest; retire every live context with its applying build before switching.

**Implementation:** [X96](delivered.md#x96--managed-libvirt-network-startup)
delivered in-tree; the actual owner restart gate remains unrun.

**Exit evidence:** collection unit tests retain explicit trusted XML and prove
bounded readiness ordering, already-enabled firewall refusal, fresh apply
probing, exact ownership and partial-removal recovery without touching foreign
units, links or overrides; external-only providers create no barrier. Request
goldens and Go evidence tests require the frozen readiness identity, owned
enabled active completion and owned-resource absence. `make check` and
`make race` qualify the change in-tree. The owner then runs the three-node
fresh apply, controller host restart, automatic network and managed-service
return, `machine start` of all three guests and safe destroy, recorded on
B466's row. Acceptance in conversation is sufficient after the actual run;
consent without that run does not satisfy either item.

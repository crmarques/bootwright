# M1 — Foundations

Deliver substrates, infrastructure components and Machines: provider and
machine realization, operating-system installation, shared service lifecycles,
identity, access, power, continuation and safe removal. The owning contracts
are [substrates](../substrates.md), [managed OS](../managed-os.md) and
[infrastructure services](../infrastructure-services.md).

[D158](backlog.md#decisions) redefines M1 on 2026-10-17 and reopens it for the
shared work below. The former hardening scope remains accepted under
[D156](backlog.md#decisions) and
[X98](delivered.md#x98--m1-owner-acceptance); its dated completion and evidence
are preserved in the [historical baseline](#accepted-hardening-baseline).
This regrouping implements no capability and creates no new acceptance claim.

[X103](delivered.md#x103--audit-defects-and-d163-screens-for-foundations-m1)
delivered the general Foundations defects of the 2026-10-18 audit and the D163
screens ([D163](backlog.md#decisions)).

**Requires:** none as a whole; each arm requires its declared host and shared
contracts. **Exit tier:** in-tree boundary/failure/replay tests and
owner-accepted provider-specific lifecycle runs; M1e requires real hardware
and independent erase proof. M1f/M1g fix their exact qualification profiles
before promotion. **Open decisions:** the existing item-level definition and
safety gates below, Registry's implementation and the two future adapters.

## Item detail

### B18

Bounded parallel block execution is delivered; what remains is the lock it
does not need but a reader does. A lifecycle operation holds the exclusive root
lock for its whole duration, so a concurrent read refuses; narrowing that to
the context lease alone would let a read such as `status` observe a running
operation. It needs [B303](delivered.md#x48--bounded-concurrent-execution) and a cross-context concurrent-install
test. The 2026-10-05 audit saw the cost: `context current`, `context list`,
`validate` and `render effective` refuse with `lifecycle.lease` for the whole
of an apply, an hour or more for a RHEL installation. Moved from M1 on
2026-10-05 (D57), when M1's journeys ran serially. D125 now requires
same-operation concurrency in M1; this item's concurrent-reader and
cross-context lock changes now belong to M1 under D158. **Exit evidence:** concurrent-reader
evidence for the narrowed lock; proof that an
operation's own blocks still see one coherent record set; and
[B265](#b265)'s exclusion, no Machine starting while its network restarts.

### B23

A lifecycle supervisor killed outright (for example by the OOM killer) runs no
handler, and ansible-core's session-isolated workers (`setsid`) survive it with
their task; run lifecycle playbooks without worker session isolation or make
the invocation a subreaper. X14 delivered the rest of S15. The 2026-10-05
audit found that turning worker session isolation off does not help, because
the workers then call `setpgid`. Moved from M1 on 2026-10-05 (D57), with
[B303](delivered.md#x48--bounded-concurrent-execution), which D125 returned to M1. **Exit evidence:** a killed
supervisor leaving no worker.

### B68

One managed `Registry` lifecycle over the shared managed-service capability
[the legacy network-service milestone](delivered.md#m1f--managed-controller-network-services) delivered. Its `LoadBalancer` half is parked as
[B100](backlog.md#b100). **Exit evidence:** a typed port, the exact
implementation, lifecycle evidence, and failure and acceptance tests.

### B70

Physical offline disk erase and managed-machine destroy on bare metal. Exact
disk identity is unproved during the controller-to-installer interval; it needs
new safety evidence that closes or explicitly bounds it. The physical managed-OS
installation narrowed that interval with an in-installer identity check but did
not close it, and deliberately kept removal retaining: a physical removal

([mutation safety](../state-reconciliation.md#mutation-safety)).
[B78](#b78) inherits it. **Exit evidence:** a separate safety contract,
an immutable target proof at erase, failure injection and real-hardware
qualification.

### B74

A bonded or VLAN installation interface for the physical Anaconda path of
[B73](#b73). One was admitted and rendered as a plain `--device` line the
installer cannot bring up until
[B289](delivered.md#x41--lifecycle-results-the-controller-stage-installation-shapes-and-bounded-runs)
made it refuse before registration, as the
[managed-OS refusal table](../managed-os.md#refusal-table) lists, and the
unused bare-metal `vlan` field left the API
([B294](delivered.md#x42--media-contexts-setup-service-and-machine-admission),
D94), so
this item defines the interface's fields (found by the 2026-10-05 audit). The
install arms B74 to B77 depend on B73 and nothing else here, so each is
separable as a bounded slice when a consumer needs it. **Exit evidence:**
renderer and executor parity for the interface and an emulated rehearsal over
it.

For M2, qualify a bond, a VLAN and a VLAN over a bond with declared parent,
members, mode, MTU, addresses/routes and install address. Existing NetworkConfig
owns intent; add no raw installer escape. Link/route readiness, unsupported
combinations, reboot and interrupted install are gates. B326 owns final
post-install networking.

**Closed (D159):** the install interface is declared in native NMState; bond,
VLAN and VLAN-over-bond install lines use Anaconda's `network` grammar
(`--bondslaves`, `--bondopts=mode=<full name>,...`, `--vlanid`,
`--interfacename`; `--device` is the declared name; no `--mtu`; the gateway
only from the install interface's default route); every available ethernet
interface is pinned with dracut `ifname=<name>:<mac>` through `mkksiso
--cmdline`, frozen in the request (libvirt MAC from the substrate, bare-metal
MAC from the proved hardware NICs); the API admits all seven bond modes; a
libvirt Machine refuses every mode but active-backup (refusal N10; other modes
are qualified on physical hosts with B78); X55 adds refusals N1 to N10 to the
managed-OS refusal table and moves request `os-install-anaconda`. The session's
X55 slice plan, 1.1, records the sources. **Open:** none; D160 accepted OD25's
defaults. Its in-tree lanes are replayed onto `m2c` from the pre-rebase branch
(D159 clause 4); the emulated rehearsal over the libvirt network-variants
example is the owner's.

### B75

The FIPS profile arm, with its secret-free or private publication. **Exit
evidence:** renderer and executor parity and a qualified FIPS install.

Target FIPS covers the installed OS boot state, crypto policy, SSH keys and
OS packages, with a reboot proof. CephX keys and Ceph daemon/service
compatibility remain M2 qualification under B472, B484 and B485.
It is distinct from controller cryptographic certification. Each incompatible
key/service refuses before installation; B346 qualifies controller access.

**Delivered in-tree (X60):** a profile enabling `fips` is admitted on a virtual
Machine, appends `fips=1` once, installs an ECDSA P-256 guest-agent host key,
refuses an Ed25519 or short RSA fleet key before registration (also when the
key is bound), proves `/proc/sys/crypto/fips_enabled` and the crypto policy
after network convergence and refuses `fips-not-enabled` otherwise; an
observation reads the same proof. Its evidence is offline: renderer and
executor parity, the refusal-table rows, the Ansible unit tests and the
architecture suite. **Acceptance baseline:** the commit that integrates X60 on

### Controller setup v2

**Why.** The owner's request of 2026-10-14 (D152): setup took more than three
minutes even after an earlier build's setup, and Fedora 43 to 44 broke it.
Today setup resolves and installs a private CPython, ansible-core and a frozen
controller DNF plan into a per-build bundle area of about 190 MB, guarded by
byte digests of glibc and libgcc, so any build or OS update repeats most of it.

**Design.** Setup installs two things, and only when they are missing.
Host packages are asked of the host's own dnf by name or RPM capability, with
a verbatim `--assumeno` preview shown before confirmation. One venv on the OS
CPython 3.12 to 3.14 (`/usr/bin/python3.X`) receives the wheels of a hash lock
each build embeds, installed by pip with `--no-index --no-deps
--require-hashes` from a content-addressed wheel cache. The automation stays in
the binary and is unpacked into root-owned staging for each Ansible launch, so
the runtime's identity is the lock digest, the Python ABI and the interpreter
path, and a live operation's closure is the lock digest and the ABI: an
`ansible/`-only fix or any rebuild with the same lock needs no setup and
continues a live operation. Setup state moves to a setup-owned subtree,
`/var/lib/bootwright/setup/` (state, lock, runtimes, wheel cache, run logs),
whose format heals itself. The cut-over bumps the registry to version 6 and the
controller record to version 3 and refuses an earlier store with the
fresh-install remedy. D152's clauses hold every choice and what was declined.

**Targets** (the owner measures before in X87's S0 and after in X90's
acceptance): a fresh setup within 60 s excluding dnf, the ready path within
2 s, a new build with the same lock within 2 s, and a runtime of at most 60 MB
and 3,000 files.

commit on local main.

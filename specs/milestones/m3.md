### M3a

Review and define the full scope and every implementation task: provider paths
and topologies, the feature-to-contract-and-gate matrix, ContainerCluster API
sufficiency, owners, dependencies, bounded outcomes, acceptance profiles and
executable exit evidence. [B473](#b473) owns the definition baseline and
completes when the owner accepts it, as D134 accepted M2a; X110's in-tree work
is the definition commit itself. **Exit:** a reviewed, traceable baseline for
M3b to M3f, with each unresolved promotion gate assigned to an item or to an
open decision below. Target contracts are written into their owning specs in
the present tense, each unmet rule with its Not-yet-met line; an item still
Needs definition keeps its proposal in its own detail. Bootwright records no
release catalog, approval or compatibility rule (D157, D162, D163): coverage
records what each acceptance run proved, and a native difference between
release minors becomes a registered version specialization. Accepting the
baseline completes no executable item or operator gate, activates no slice and
authorizes no host operation. New public fields (secondary networks, the
OVN-Kubernetes settings, libvirt per-NIC attachments and MTU, vSphere
in-cluster vCenter credentials) are written into the owning specs as proposed
targets, each with its Not-yet-met line, and MetalLB package configuration
(B727, with M4's B752 under D173) stays in B727's detail; the owner's
acceptance of this baseline approves them, as D132 required owner approval of
M2's API, and a field the owner rejects leaves the specs together with its item.

Deliver a three-node compact cluster on one libvirt host: three schedulable
masters, no compute node, platform `baremetal` with `provisioningNetwork:
disabled`, and the `api`/`api-int` and `ingress` virtual IPs owned by the
installer's own VIP holders on the managed network. The platform follows who
answers the endpoints: installer-owned virtual IPs on `baremetal`, an external
or load-balancer address on `none`, never both ([B707](delivered.md#b707), a pre-existing
defect). An endpoint address belongs to one cluster and to nothing else
Bootwright declares ([B708](delivered.md#b708)), and a virtual IP that already answers
refuses before boot ([B709](#b709)). Each media insert gets its own token
([B314](delivered.md#b314)). Booted nodes are proved to answer on the network within the
boot budget ([B710](#b710)); a bootstrap wait that fails names each declared
node the assisted service does not hold ready ([B260](#b260)); media is
released only after the read proves every declared node, and a rendezvous host
stranded by another host's error is named ([B711](delivered.md#b711)). Installations of one
context run one at a time ([B712](delivered.md#b712), Q5). [B713](delivered.md#b713) delivers the
lab-compact example and the multi-node plan, continuation, resolution and
removal journeys that the [retired](backlog.md#retired) B62, B63 and B65 named
without bounding. A context that holds a completed lab-sno apply destroys it
before lab-compact is applied there (D153).

live rehearsal belongs to the first profile that declares an external load
balancer (M3d's networking profile or M3e). A managed `LoadBalancer`
([B100](backlog.md#b100)) stays parked: the compact profile needs none.

### B714

**In-tree delivery, 2026-10-23:** implementation and host-independent probes
are delivered by the independent completion work below. Its operator evidence
and prerequisite acceptance remain open.

**Outcome.** One `cluster-install-<cluster>` block installs a cluster of any
size the run ceiling admits. Its per-node phases (the state reads, the pre-boot
proof, the insert, the boot selection, the power-on, the readiness proof of
[B710](#b710), and the release) run concurrently, at most a frozen fan-out of
nodes at a time; its boot budget and deadline grow with rounds, not nodes;
workers, infra nodes and four or five masters are projected and covered by
goldens; one node that never comes up fails the block naming it, before any
installer wait.

**Owners:** Container cluster and Substrate, with State reconciliation for the
runner's per-node inventory. **Contract:** the Boot and Budgets paragraphs of
[Installation](../openshift-clusters.md#installation) and
[cluster size](../openshift-clusters.md#cluster-size).

- *Fan-out.* Each node's install request entry freezes its arm's controller
  kind: `emulated` (a libvirt provider's sushy-tools controller) or `physical`
  (a bare-metal BMC). The kind's fan-out is 4 for `emulated`, because every
  insert makes the emulator on the one provider host download the image and
  write it into its virtual-media pool, and 16 for `physical`, because each BMC
  fetches from the artifact server on its own. A cluster freezes `fanOut`, the
  smallest fan-out among its nodes' kinds. Rounds are `r = ceil(n / fanOut)`.
  The KubeVirt and vSphere fan-out and allowance are fixed by
  [B87](m1.md#b87) and [B99](m1.md#b99).
- *One table of arm constants.* [B704](delivered.md#b704) has each arm publish its
  entry-point bounds and boot allowance as Go constants; B714 freezes them per
  node. Whichever of the two lands second moves the other's figures into that
  one table.
- *Boot budget.* `max(900, b x r)` seconds, where `b` is the per-round boot
  budget of the slowest kind present: 600 seconds `emulated`, 1,800 seconds
  `physical` (v1 needed 1,800 seconds for a physical live image to reach sshd;
  re-verified on the first physical run). One deadline is taken before the
  first round, and every step of every round runs under what is left of it.
- *Readiness.* Each round runs B710's proof per node; B710 owns the proof and
  its failure, B714 owns when it runs. A node that fails it fails the boot
  phase naming it, its Machine and the address, after the other nodes of its
  round finish; nodes already running from this cluster's image take none of
  the budget, as today.
- *Release.* Release runs in rounds only after the read of
  [B711](delivered.md#b711) proves every declared node.
- *Deadline.* The boot budget plus the bootstrap and installation waits of
  5,400 seconds each, plus 30 minutes, plus `r x m`, where `m` is the round
  margin of the slowest kind present: two media reads, an eject and a boot
  selection of that kind, 11 minutes `emulated`; the `physical` margin is
  [B67](#b67)'s derivation.
- *Ceiling.* A cluster whose deadline passes the 6-hour ceiling refuses before
  registration, naming its deadline and how many nodes fit. With these values:
  7 rounds of 4, so 28 nodes, behind emulated controllers (`max(900, 600 x 7) +
  12,600 + 7 x 660 = 21,420` seconds); behind physical controllers `16 x
  floor(9,000 / (1,800 + m))` nodes, which is at least 32 while `m` is at most
  45 minutes. One to four emulated nodes keep today's 3 h 56 min.
  [Q14](#m3a-open-decisions) decides whether this bound stands.
- *Waits.* The two installer waits keep their 5,400-second budgets and their
  resumable classes; the agent `install-complete` budgets 40 minutes of
  initialization and 30 of stability after a 60-minute bootstrap window, and no
  60-minute bare-metal extension is assumed (uncertain). Waits do not scale
  with nodes: workers join concurrently and the in-cluster assisted controller
  approves every pending certificate request while the installation runs.
- *One never-registering node.* The rendezvous host starts the installation
  only when every declared host is `known`, so one node that never registers
  holds the whole cluster. The readiness proof catches a node that never booted
  its image; a node that booted but never registered is named by the stall
  diagnosis of [B260](#b260). Neither is tolerated as `n - 1`: the remedy is to
  repair the node and repeat the apply (which boots only nodes not running this
  cluster's image), or to destroy and declare the cluster without it. A cluster
  never starts with fewer nodes than it declares.
- *Workers, infra, four and five masters.* `controlPlane.replicas` and
  `compute[0].replicas` are always rendered, including `0` (omitted compute
  means three expected workers); every host carries its `role`; infra nodes
  install as `worker`; the rendezvous host stays the first master in node-name
  order. Four and five masters are the general topology rule's already. No
  sizing rule is added: the role floors each release's image enforces are
  evidence (D163).
- *Implementation.* The install adapter run gets one inventory host per node,
  each `ansible_connection: local` on the controller and grouped by phase,
  beside the controller host; the per-node phases run as plays over the node
  hosts with `throttle` set to the frozen `fanOut`, and the waits, the
  kept-kubeconfig handling and the completion read stay plays on the controller
  host. A failed node host leaves the others running; the phase then fails the
  block naming every failed node.

**Exit evidence:** the deadline test of the agent-install package rewritten for
rounds (the margin test derives `m` per kind from the per-node task files; boot
budgets and deadlines pinned at 1, 4, 5, 28 and 29 emulated nodes, and at 16,

[node networking](../openshift-clusters.md#node-networking).

  interfaces, static addresses, routes and resolvers (the documented subset).
  An `ovs-bridge`, `ovs-interface`, `ovs-port` or `linux-bridge` interface, or
  an `ovn` or `ovs-db` section, refuses: `nmstatectl gc` carries no `ovn` or
  `ovs-db` state and bridges in agent `networkConfig` are unproven; such a
  bridge is declared as a secondary network ([B726](#b726)) instead, or waits
  for [B740](backlog.md#b740).
- An interface named as OVN-Kubernetes reserves refuses: the documented
  reserved names (`br-ext`, `br-int`, `br-local`, `br-nexthop`, `br0`,
  `ext-vxlan`, `ext`, `int`, `tun0`, and names starting `genev_sys_`, `k8s-`,
  `ovn-k8s-`, `patch-br-`, `vxlan_sys_`) plus `br-ex`, which Bootwright adds
  because `configure-ovs` builds it from the default-route interface.
- A node whose install address is not on the interface carrying its default
  route refuses, because `configure-ovs` builds `br-ex` from the default-route
  interface on every boot and the node would then answer on another one.
- Every `ethernet` interface that is a bond port carries its permanent MAC as
  `mac-address` with `identifier: mac-address`, because a bond member's running
  MAC is the bond's (observed by v1; re-verify on this tree); no `bond` or

  addressless NIC: the substrate realizes it (a virtual NIC on its own
  attachment with [B701](delivered.md#b701), a declared NIC on a physical node) and
  `agent-config` lists it with its MAC like any other.
- Interface `mtu` values pass through as declared; Bootwright never derives one
  (the MTU is a capability the attachment declares,
  [B702](delivered.md#b702)).
- Bonds of any mode are accepted and the installer and the switch judge them;
  only `active-backup` is rehearsed on libvirt, whose Linux bridge cannot do
  LACP.
- The agent renames a logical interface name to the device's kernel name on the
  live image, so a node's `ethernet` names are its kernel names after
  installation, which is what a secondary network's uplink and a MetalLB
  advertisement must name; bond and VLAN names are kept. The emulated
  rehearsal records the kernel names libvirt NICs take.

**Implementation pointers:** `internal/containercluster/agentinstall/projection.go`

**Outcome.** A cluster declaring `spec.networking.secondaryNetworks` gives
in-cluster pods and VMs layer-2 access to external networks through
OVN-Kubernetes localnet: after installation the block `cluster-network-<cluster>`
applies, per node, one `NodeNetworkConfigurationPolicy` with the OVS bridges and
bridge mappings, then one `ClusterUserDefinedNetwork` per network, whose
`NetworkAttachmentDefinition`s OVN-Kubernetes renders. The block applies
secondary networks only: MetalLB's pools and advertisements are the MetalLB

and [post-installation network configuration](../openshift-clusters.md#post-installation-network-configuration).
The delivery route is [Q10](#m3a-open-decisions), option b.

- *Typed intent.* `spec.networking.secondaryNetworks[]`: `name`; `topology:
  Localnet`; `uplink` either `{bridge: br-ex}` (share the default bridge;
  required where a node has one NIC) or `{interface, bridge}` (a node interface
  Bootwright bridges into a new OVS bridge of that name); optional `vlan` (an
  access VLAN 1 to 4094); optional `mtu` (576 to 65,536, at least 1,280 with an
  IPv6 subnet); `ipam` `{mode: Disabled}` (default, and the only mode a VM
  network supports) or `{mode: Enabled, subnets, excludeSubnets, lifecycle}`;
  required `namespaceSelector.matchLabels`.
- *Admission.* `name` is a DNS label other than `physnet` and `exgwphysnet`, the
  physical network names OVN-Kubernetes reserves, and contains no `,` or `:`. An
  `uplink.interface` exists on every node as an addressless `ethernet`, `bond`
  or `vlan` ([B718](#b718)) that is neither the install interface nor a reserved
  name; `uplink.bridge` is at most 15 characters, not reserved, and names one
  interface on every node. Networks sharing an uplink declare distinct `vlan`s
  (at most one untagged), because two NADs on one VLAN break OVN-Kubernetes.
  `mtu` does not exceed the uplink interface's declared MTU (1,500 when
  undeclared). `Enabled` needs one or two `subnets` of different families;
  `excludeSubnets` (at most 25) lie inside them and need them; `lifecycle:
  Persistent` needs `Enabled`. A cluster with secondary networks needs a binding
  that selects a package or add-on providing `nmstate`.
- *Rendering.* Per node, `nmstate.io/v1 NodeNetworkConfigurationPolicy` named
  `bootwright-<node>` with `spec.nodeSelector` `kubernetes.io/hostname: <node>`
  and a `desiredState` holding, for each distinct `{interface, bridge}` uplink,
  an interface `{name: <bridge>, type: ovs-bridge, state: up, bridge:
  {allow-extra-patch-ports: true, options: {stp: false, mcast-snooping-enable:
  true}, port: [{name: <interface>}]}}`, and `ovn.bridge-mappings[]` (`localnet:
  <name>`, `bridge: <bridge or br-ex>`, `state: present`); ovnkube-node
  preserves these mappings beside its own `physnet`. Per network,
  `k8s.ovn.org/v1 ClusterUserDefinedNetwork` `<name>` with
  `spec.namespaceSelector`, `spec.network.topology: Localnet` and
  `spec.network.localnet` (`role: Secondary`, `physicalNetworkName: <name>`,
  `ipam`, `subnets`, `excludeSubnets`, `mtu`, `vlan: {mode: Access, access:
  {id}}`) as declared. Bootwright creates no namespace: the CUDN renders a NAD
  named `<name>` into every namespace its selector matches, as they appear.
- *Order and readiness.* The block requires the cluster's install block and the
  instance that provides `nmstate`; it applies every NNCP, waits for each
  `Available` `True` (`Degraded` `True` fails naming the node's enactment,
  `Ignored` with `NoMatchingNode` fails naming the selector), then every CUDN,
  and waits for `NetworkCreated` `True`; a `SyncError` naming a foreign NAD fails
  naming it.
- *Ownership and lifecycle.* Objects are created and recorded through
  [B750](delivered.md#b750)'s program and [B751](delivered.md#b751)'s adapter (create-only
  with a field manager; an existing object is compared, never patched); a
  same-name foreign object refuses; a continuation's replay reports
  `unchanged` for equal objects and fails naming any difference (a localnet
  CUDN is immutable); a settled apply attests its records and contacts no

  instance retires ([retirement](../add-ons.md#retirement)), and contacts

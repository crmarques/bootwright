# M4 — Cluster add-ons

Define add-on delivery in [M4a](#m4a), then install built-in add-on packages
on OpenShift clusters the context builds: [M4b](#m4b)'s skeleton (built-in
packages selected and configured in a binding, the cluster object program and
its adapter, one instance block per package and cluster, owned cluster
Secrets and the package listing, proved on the Kubernetes NMState Operator),
[M4c](#m4c)'s network add-on (MetalLB and its layer 2 pools), [M4d](#m4d)'s
IBM Fusion Data Foundation in external mode over the Ceph cluster M2 manages,
[M4e](#m4e)'s Red Hat Advanced Cluster Management and Red Hat OpenShift
GitOps with its bootstrap object, and [M4f](#m4f)'s GitLab (D173). The
[add-on lifecycle](../add-ons.md) owns runtime behavior, the
[add-on API](../api/addons.md) the fields, and the
[coverage page](../add-on-coverage.md) the package matrix and acceptance
profiles; its profiles are examples, not product limits. The
[product scope](../project.md#product-scope) names these packages among the
cluster-bound integrations. Packages are built into the executable; authored
(custom) packages are [B90](#b90)'s, first slice X235. The Ceph side is a cluster M2
manages (D19, D128); an external Ceph cluster is parked as
[B107](backlog.md#b107). Every instance is retired with its cluster: removing
one add-on from a running cluster is parked as [B769](backlog.md#b769), and
publishing application or fleet GitOps content stays a
[non-goal](../project.md#design-priorities-and-non-goals).

**Requires:** M2 and M3c (D172) and, per submilestone below, M3's
[B64](delivered.md#b64) for every slice that runs an instance block, M3b's or M3c's
accepted cluster for each operator gate, M3c's [B708](delivered.md#b708) and M3d's
[B719](m3.md#b719) and [B726](m3.md#b726) for M4c, M2's managed Ceph cluster
and resources for M4d, and M4d's accepted row for M4f's gate.
Whether M2 binds the items M3d's networking needs is
[Q25](m3.md#m3a-open-decisions). Accepted by the owner for implementation
([D174](backlog.md#d174), applying [D173](backlog.md#d173) (6), Q59): M2 and
M3c are waived for the implementation of M4b to M4f's slices only, each slice
keeping the M2 and M3 slices its row names; D174 applied the waiver to M4b and
M4c, and [D180](backlog.md#d180) to the independent blockers of M4d and M4e.
Promotion, operator gates and M4 completion keep every Requires. **Exit tier:** an emulated rehearsal per
submilestone on libvirt+sushy, each an owner-accepted ledger row: M4b and M4c
on M3b's single node, M4d with an M2-managed virtual Ceph cluster beside
M3c's compact cluster, M4e on M3c's compact cluster and M4f on a fresh apply
of M4d's topology; real hardware is not an M4 exit tier, because D17's "M4"
is the pre-D128 Ceph milestone, now M2 (D173; owner question
[Q61](#m4a-open-decisions)). **Open decisions:** Q26 to Q61
in [M4a's open decisions](#m4a-open-decisions), whose recommended baseline
D174 accepted, Q135 to Q138 there, [Q25](m3.md#m3a-open-decisions) on M3's
page, and the open session clauses of D173. No
open question is an implicit permission, a passed gate or a supported
feature.

M4a is accepted. The in-tree implementations of M4b to M4e, with their
host-independent evidence, are recorded in [delivered](delivered.md) (X136 to
X152).

### M4a

Review and define the full add-on scope and every implementation task: the
built-in package model and its selection, the typed configuration of each
package, the cluster object program and its adapter, ownership, OLM
determinism, readiness, retirement, Secrets reaching a cluster, the package
matrix, owners, dependencies, bounded outcomes, acceptance profiles and
executable exit evidence. [B749](delivered.md#b749) owns the definition baseline and
completes when the owner accepts it, as D134 accepted M2a and D172 proposed
M3a; X135's in-tree work is the definition commit itself. **Exit:** a
reviewed, traceable baseline for M4b to M4f, with each unresolved promotion
gate assigned to an item or to an open decision below. Target contracts are
written into their owning specs in the present tense, each unmet rule with
its Not-yet-met line; an item still Needs definition keeps its proposal in
its own detail. Bootwright registers no default channel, CSV or catalog
image, no version pairing and no compatibility rule (D157, D162, D163): the
operator declares every channel and CSV, coverage records what each
acceptance run proved, and a native difference between release minors becomes
a registered version specialization. Accepting the baseline completes no
executable item or operator gate, activates no slice and authorizes no host
operation. New public fields (`ClusterAddonBinding.spec.packages` with one
configuration shape per package, and `StorageExport`'s managed arm with
`cephxKeyType`) are written into the owning specs as proposed targets, each
with its Not-yet-met line; the owner's acceptance of this baseline approves
them, as D132 required owner approval of M2's API, and a field the owner
rejects leaves the specs together with its item.

### B727

MetalLB address pools and their layer 2 advertisements are the `pools` of the
[MetalLB package](#b84)'s configuration in its `ClusterAddonBinding`, never
the cluster's. The owner asked for MetalLB "to be installed and configured as
add-on, after initial implementation of M4" ([D172](backlog.md#d172)),
so `ContainerCluster` gains no load-balancer field. The contract is
[package metallb](../api/addons.md#package-metallb). Redefined on 2026-10-20
(D173): the package-configuration shape is closed by
[B752](delivered.md#b752)'s `spec.packages.metallb`; admission is the package's `Admit`
hook over the `ClusterFacts` fields of [B756](delivered.md#b756) and [B758](#b758); the
advertisement names at most one interface (`l2.interface`), because a pool
lies inside one subnet; the forwarding question is closed by Q34 (a), the
cluster's `ipForwarding: Global`; the `MachineConfig` specialization question
leaves the item, because nothing registers one until a run shows it is needed
(D162); "pool status reported as evidence" becomes an operator reading at the
gate, because a program check has no read-only reporting arm; and B719 and
B726 leave Requires for B758, which reads them.

- *Configuration.* At most 16 pools. Each pool has a `name` (a DNS label),
  `addresses` (1 to 16 canonical CIDRs or `<first>-<last>` ranges),
  `autoAssign` (default `true`) and an optional `l2.interface`.
- *Rendering.* After the `MetalLB` resource reports `Available`, and after
  the `ipaddresspools.metallb.io` and `l2advertisements.metallb.io`
  CustomResourceDefinitions report `Established`, each pool becomes
  `metallb.io/v1beta1 IPAddressPool` `<name>` in `metallb-system`, with
  `spec.addresses` and `spec.autoAssign`. It also becomes
  `metallb.io/v1beta1 L2Advertisement` `<name>` in `metallb-system`, with
  `spec.ipAddressPools: [<name>]`, plus `spec.interfaces: [<interface>]` when
  one is declared. Every pool has its advertisement, because a pool no
  advertisement selects allocates addresses nobody announces. Creating an
  object proves it present, and the program's comparison on continuation
  proves it unchanged; no further check is needed.
- *Machine-network pool.* A pool without `l2.interface` lies inside one
  consumed machine network of the cluster and announces on every interface.
- *Secondary-interface pool.* A pool with `l2.interface` names an interface
  that every node declares, and that carries on every node a static address of
  the pool's family. All those addresses lie in one subnet, which holds the
  pool. A node without the interface would silently not announce when elected.
  The interface is not a node's default-route interface and not `br-ex`,
  because OVN-Kubernetes builds `br-ex` from the install interface. It is not
  a secondary network's uplink interface or bridge, which carry no host
  address. The cluster declares `gatewayConfig.routingViaHost: true` and
  `gatewayConfig.ipForwarding: Global` ([B719](m3.md#b719)), the host routing
  and forwarding the documentation requires on a secondary interface.
- *Exclusions.* No pool includes:
  - an effective `api`, `api-int` or `ingress` address;
  - an address of the cluster's nodes;
  - a next hop of a node's route;
  - an address another declared object holds (another cluster's endpoint, a
    Machine's address, a managed DNS, NTP, Proxy, ArtifactServer or Registry
    bind or endpoint address, a LoadBalancer bind address, a managed libvirt
    network's host address);
  - an IPv4 network or broadcast address of its subnet.

  No pool overlaps another pool, a cluster or service network, or a secondary
  network's subnets. The reason is that keepalived and MetalLB would both
  answer for one address, and the documentation forbids addresses "in use by
  other network devices".
- *Changes.* Pools change only by destroying and applying again (D153). An
  operator who manages pools after installation selects `pools: []`.
- *Not this item.* MetalLB never serves `api`, `api-int` or the default
  ingress, which exist before it can. The default IngressController stays
  `HostNetwork` on non-cloud platforms. A version specialization of forwarding
  is registered only if a run shows `ipForwarding: Global` failing, where the
  cluster's release discriminates (D162, D163).

secondary-interface pool and the largest admitted configuration (16 pools of

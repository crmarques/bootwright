# M4 — First add-ons

The first add-ons: ingress through MetalLB, and the integration of OpenShift
with a Ceph cluster through IBM Fusion Data Foundation. The
[product scope](../project.md#product-scope) names both packages among the
cluster-bound integrations. The Ceph side is a cluster M2 manages (D19, D128); an
external Ceph cluster is parked as [B107](backlog.md#b107). An example package
already exists at
[`examples/full-platforms/multidc-platform/add-ons/fusion-data-foundation`](../../examples/full-platforms/multidc-platform/add-ons/fusion-data-foundation/add-on.yaml).

**Requires:** M3c, for a supported cluster (D172), and M2, for the Ceph cluster.
Whether M2 binds only B85 and B86, the Ceph integration items, so that D172's
implementation waiver reaches the items M3d's networking needs (B83, B84,
B727, B735), is [Q25](m3.md#m3a-open-decisions). **Exit tier:** an emulated
rehearsal until B83's definition fixes it. **Open decisions:**
[Q25](m3.md#m3a-open-decisions) on M3's page; none numbered here.

## Item detail

### B83

One built-in add-on package and binding lifecycle, with no exact package,
target or release selected yet. **Exit evidence:** the
[package and driver design](../deferred/add-ons-design.md), compatibility,
trust and secrets, readiness, ordering, replay and destroy, and acceptance on a
supported cluster.

**M3d requirements (2026-10-20, D172).** M3d's networking profile consumes this
lifecycle for built-in OLM operator packages ([B84](#b84), [B735](#b735)), and
M3d's cluster-network block ([B726](m3.md#b726)) consumes three ports of this
lifecycle: cluster access through [B64](m3.md#b64)'s lent kubeconfig (B64
provides it); typed Kubernetes object apply with ownership receipts (Bootwright-named objects created, a context- and
operation-specific server-side-apply field manager, the API's UID and the
desired digest recorded, a same-name foreign object refused, never
`--force-conflicts`); and readiness by `csvSucceeded`, `condition` and
`resourceExists` under one absolute deadline inside the 6-hour ceiling. B83
owns the second and third; it requires nothing from B726. An
instance on a cluster the same removal destroys (virtual nodes) or retains
(physical nodes) is retired with that cluster and never removed online, so no
M3d removal contacts a cluster. The Subscription's `channel` and `startingCSV`
are the operator's declaration (D163); how a built-in OLM package pins its
catalog content when it targets the cluster's default `redhat-operators` source
is an open question of this item. The lifecycle also defines the typed package
configuration a binding carries, because binding inputs are scalar names today
and [B727](#b727) needs a structured one.

### B727

MetalLB address pools and L2 advertisements, configured by the MetalLB package
of [B84](#b84) and not by the cluster. The owner asked for MetalLB "to be
installed and configured as add-on, after initial implementation of M4"
([D172](backlog.md#decisions)), so the cluster declares no pool and
ContainerCluster gains no load-balancer field.

**Contract:**

- *Typed configuration.* The pools and advertisements are the package's typed
  configuration in its ClusterAddonBinding, in the package-configuration shape
  [B83](#b83) defines. Binding inputs are scalar names today, so B83 adds one.
  A pool has a `name`, `addresses[]` (CIDRs or `start-end` ranges) and
  `autoAssign` (default `true`); its L2 advertisement has optional
  `interfaces[]`, and an omitted list announces on every interface.
- *Admission.* Each pool lies inside one network: a consumed machine network
  when it names no interface, otherwise the subnet of the address every node
  carries on each named interface. Every node carries every named interface,
  because a node elected without it silently does not announce. No pool
  includes an `api`, `api-int` or `ingress` endpoint address, a node address, a
  route next hop of its network, or a managed DNS, NTP, Proxy, ArtifactServer
  or Registry endpoint address, nor overlaps another pool, a cluster or service
  network or a secondary network's subnets, because the keepalived VIPs and
  MetalLB would both answer for one address.
- *Rendering.* `metallb.io/v1beta1 IPAddressPool` `<name>` in `metallb-system`
  with `spec.addresses` and `spec.autoAssign`, and `metallb.io/v1beta1
  L2Advertisement` `<name>` with `spec.ipAddressPools: [<name>]` and
  `spec.interfaces` when declared. Readiness is each object present; a pool
  `status`, when the object carries one, is reported as evidence and is never
  required (the 4.21 documentation describes it).
- *Secondary interface.* A binding that advertises on an interface other than
  the default-route one requires its cluster to declare the OVN-Kubernetes
  `routingViaHost: true` that [B719](m3.md#b719) renders at install time, and
  refuses otherwise. Forwarding on that interface is one general mechanism of
  the MetalLB package's driver: either `ipv4.forwarding: true` for the
  interface in the node's NNCP, which needs an `nmstate` provider
  ([B735](#b735)), or a cluster that declares the OVN-Kubernetes
  `ipForwarding: Global` B719 renders. Evidence, not a seam: the 4.20 and 4.21
  documentation enables forwarding with a `MachineConfig` sysctl
  (`net.ipv4.conf.<interface>.forwarding = 1`) or with `ipForwarding: Global`,
  and the 4.22 documentation with the NNCP. A version specialization is
  registered only if a run shows the general mechanism failing where a
  provable artifact or cluster fact discriminates, with its catalog row and a
  parity test (D162, D163). A pool advertised on a secondary network waits for
  [B726](m3.md#b726).
- *Not this item.* MetalLB never serves `api`, `api-int` or the default
  ingress, which exist before it can; the default IngressController stays
  `HostNetwork` on non-cloud platforms.

**Open questions:** the package-configuration shape, with B83; which general
forwarding mechanism the driver uses (the NNCP or `ipForwarding: Global`); and,
only if a run registers a `MachineConfig` specialization, whether it is (a)
applied after installation through the package driver, accepting one rolling
reboot, or (b) an install-time manifest through B719, which would then admit a
binding-sourced `MachineConfig`. Recommendation: (a), keeping B719's sources
cluster-only so X123's scope does not move. **Exit evidence:**
rendering goldens for a machine-network pool and a secondary-interface pool;
admission tests for each overlap and the interface rule; a binding admission
test for the `routingViaHost` rule; if a specialization is registered, its
catalog row in `.agents/knowledge/version-specializations.md`,
`TestDocsVersionSpecializationCatalogMatchesRegistries` and a parity test. It
completes in-tree and then awaits operator acceptance on B729's ledger row.
Operator gate: [B729](m3.md#b729).
